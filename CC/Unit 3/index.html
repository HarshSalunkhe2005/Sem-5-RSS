01 · Every cloud service fits one of these three layers EXAM SCOPE

Cloud Architecture — Layers & Models

Cloud architecture refers to the components — databases, software capabilities, applications — that companies use to leverage cloud resources for business problems. The stack is built as three layers, each renting out a different amount of control to the customer.

SaaS — Software as a Service
The application itself. Provider manages everything.
PaaS — Platform as a Service
Dev/test/deploy environment. Provider manages infra + runtime.
IaaS — Infrastructure as a Service
Raw compute, storage, network. Provider manages only hardware.

IaaS — Infrastructure as a Service

The basic layer — hardware and network. What distinguishes it from a regular hosting company: scalability and virtualization. Providers scale so the marginal cost of more storage/bandwidth is minimal, and virtualization lets them use up to 90% of compute resources vs idle traditional servers. Example: Gmail's ~8GB free storage per user, backed by Google's giant data centers.

Key Features

  • Highly scalable resources
  • Enterprise-grade infrastructure
  • Cost depends on consumption
  • Multitenant architecture — one piece of hardware serves many users
  • Client gets complete control over the infrastructure

Adv / Disadv

+ Most flexible/dynamic model, pay-as-you-go, automated hardware deployment, virtualized management frees up staff time.

− Data-security issues from multitenancy, vendor outages block access, teams need training on new infra.

PaaS — Platform as a Service

Provides resources to actually build applications — combined with IaaS it lets you develop, test, run and host applications, supporting the entire lifecycle from build → test → deploy → maintain → update. Includes infra plus dev tools, DB management systems, etc. Example: Microsoft Azure — full dev+deploy environment with hosting.

Key Features

  • Develop, test, host apps in the same environment
  • Resources scale up/down with business needs
  • Multiple users can access the same app in development
  • User does not have complete infra control
  • Web services & DBs integrated; remote teams collaborate easily

Adv / Disadv

+ Highly scalable/available/multi-tenant, quickened+simplified dev, reduced cost & coding, automated policy, easy hybrid-cloud migration.

− Data security, existing-infra compatibility, dependency on vendor's reliability/support.

SaaS — Software as a Service

The actual software — organizations rent the usage of a SaaS application and users connect over the internet; the app must be web-based/accessible from anywhere. Provider offers both software and hardware. It makes no sense to ask "cloud or SaaS?" — SaaS is simply a layer in the cloud stack.

Key Features

  • Subscription model
  • No download/install/upgrade needed
  • Resources scale with requirements
  • Accessible from any connected device
  • Provider is responsible for everything

Adv / Disadv

+ No hardware/setup cost, automated upgrades, cross-device, accessible anywhere, pay-as-you-go, scalable, easy customization.

− Loss of control, limited solution range, connectivity is mandatory.

Cloud Service Provider

A third-party company offering a cloud-based platform, infrastructure, application, or storage service — pay only for what you use, like a utility (electricity/gas). Benefits: scalability & flexibility (no physical-server limits), reliability (multiple redundant data centers), customisation, and responsive load balancing. Trade-off: businesses must still evaluate security — access controls and compliance configurations for data stored in someone else's cloud.

02 · What every cloud app actually needs EXAM SCOPE

Architecture for Cloud Applications

A cloud application's architecture is built on top of the IaaS/PaaS/SaaS stack above: the provider's infrastructure and platform layers host the application's own frontend, backend, and data layers. Designing this architecture is a step-by-step process — collect requirements → analyze → design → evaluate/improve → deliver → operate continuously — governed by 6 design principles.

6 Principles of Cloud Architecture Design

1️⃣ Reasonable Deployment

Public cloud = VMs + high-performance physical hosts. Private deployment = packaged independent software for a select user base. Hybrid = unified management across public cloud + private platforms (VMware, OpenStack, physical servers).

2️⃣ Business Continuity

High Availability — redundancy prevents interruption. Continuous Operations — fault-free uptime. Disaster Recovery — restore apps/data in a different environment after damage.

3️⃣ Elastic Expansion

Decouple components (dynamic vs static data) first: stay stateless (state in Redis), add load balancing, decouple via message queues/API Gateway, enable global load balancing across hybrid/multi-cloud.

4️⃣ Performance Efficiency

Compute: higher-config hosts + clusters. Storage/caching: Redis hot-data cache, in-memory compute. Network: pick the optimal data center per region.

5️⃣ Security Compliance

Separate master/sub-accounts & key pairs, least-privilege roles, ACLs + security groups, VPC isolation, prevent DDoS/SQLi/XSS, keep access & operation logs.

6️⃣ Continuous Operation

Monitor resources/services/events, alert via phone/SMS/email, auto-handle via callback functions, auto-scale on CPU/metrics, track cost and alarm on balance to avoid runaway spend.

03 · What a production cloud app must satisfy EXAM SCOPE · high-yield

Cloud Application Requirements

Building a cloud application is a 12-step requirement checklist — each with a concrete example of what "good" looks like.

  1. Requirement Analysis — identify the business problem/objectives, determine user requirements, analyze workload patterns. e.g. an online-learning platform needs video streaming, authentication, assessment modules.
  2. Scalability — support increasing/decreasing workloads, allocate resources dynamically. e.g. online exams auto-add servers under load.
  3. Availability — stay accessible with minimal downtime via redundancy/failover. e.g. e-commerce sites must stay up during festive sales.
  4. Reliability — perform consistently without failure; data integrity + fault tolerance. e.g. banking apps must complete every transaction accurately.
  5. Performance — fast response times via load balancing + resource optimization. e.g. shopping-site search results in seconds.
  6. Security — protect data/apps/infra: authentication, authorization, encryption, auditing. e.g. healthcare systems securing patient records.
  7. Data Management — efficient storage/retrieval/backup/recovery, distributed DBs + big-data support. e.g. social media storing billions of posts/images.
  8. Interoperability — work across different cloud platforms via standard APIs/protocols. e.g. an AWS-deployed app interacting with Azure-hosted services.
  9. Elasticity — auto-provision/release resources on demand, pay only for what's used. e.g. video-streaming services add capacity for a live event.
  10. Cost Efficiency — optimize utilization, pick the right service model (IaaS/PaaS/SaaS). e.g. startups use SaaS to skip infra costs.
  11. Compliance & Governance — adhere to legal/regulatory policy, maintain audit trails/data-privacy standards. e.g. financial institutions complying with RBI/data- protection regulation.
  12. Monitoring & Maintenance — continuously monitor performance/usage; logging, alerting, automated maintenance. e.g. cloud monitoring tools detecting server failure and notifying admins instantly.

04 · How cloud apps are decomposed into independent services EXAM SCOPE

Service-Oriented Architecture (SOA) for Cloud Applications

SOA structures an application as a collection of loosely-coupled, independently deployable services, each implementing one business capability, communicating over a network.

🙋Service Consumer

The client/application requesting a service — web app, mobile app, or another service. e.g. a customer placing an order on an e-commerce site.

🏭Service Provider

Creates and provides the service, publishing its details for consumers. e.g. a Payment Service exposing online payment functionality.

📇Service Registry

Directory of available services enabling dynamic discovery. Examples: UDDI, Eureka Server, Consul.

🚌Enterprise Service Bus (ESB)

Middleware enabling inter-service communication: message routing, data transformation, load balancing, security enforcement, protocol conversion.

🧩Cloud Services

Each business capability as an independent service — Authentication, Inventory, Payment, Shipping, Notification.

☁️Cloud Infrastructure

Supplies compute, storage, networking, virtualization underneath every service. AWS EC2, Microsoft Azure, Google Cloud Platform.

SOA is what makes a cloud application elastic and interoperable (Requirements 8 & 9 above) — each service scales independently and can be swapped or upgraded without touching the rest of the system.

05 · Using the cloud's near-unlimited resources at once EXAM SCOPE

Parallelization within Cloud Applications

Parallelization is dividing a large computational task into smaller tasks executed simultaneously across multiple processors, VMs, containers, or cloud resources. Cloud computing's virtually unlimited resources make parallel execution efficient and scalable.

Why parallelize in the cloud

⏱️ Reduce execution time

🚀 Improve performance

📊 Handle large-scale data

📡 Real-time analytics

Example: processing millions of customer transactions on an e-commerce platform simultaneously instead of one-by-one.

Common parallelization patterns

PatternHow it worksCloud example
Data ParallelismSplit a large dataset into chunks; run the same operation on each chunk concurrently, merge results. MapReduce / Apache Spark processing a large log file across worker nodes.
Task ParallelismSplit a workflow into different independent sub-tasks that run concurrently. A video-transcoding pipeline running audio-extraction, thumbnailing, and compression at once.
Pipeline ParallelismBreak a task into sequential stages; different items flow through different stages simultaneously. An ETL pipeline where one batch is being transformed while the next is being extracted.
Request-level ParallelismMultiple independent user requests served concurrently by auto-scaled, stateless service instances. A load-balanced web-app tier handling thousands of simultaneous HTTP requests.

06 · Structuring an app into independent layers EXAM SCOPE

Multi-Tier Application Architecture

Multi-tier (N-tier) architecture physically separates an application's presentation, processing, and data logic into independent tiers — each can be developed, deployed, scaled, and secured separately, which is exactly what makes an app a good fit for elastic cloud infrastructure.

Presentation Tier
UI the user interacts with — web/mobile frontend, HTML/CSS/JS or a mobile app.
Application (Logic) Tier
Business logic, processing, APIs — the "brain" of the app, often itself split into microservices.
Data Tier
Databases & storage — SQL/NoSQL, file/object storage, caches.

Why go multi-tier instead of one monolith?

📈Independent Scaling

Scale the busy tier (e.g. the app/logic tier under load) without over-provisioning the others.

🔐Better Security

The data tier can sit in a private subnet, never directly exposed to the internet — only the app tier can reach it.

🔧Independent Maintenance

Update/redeploy one tier (e.g. the frontend) without touching the others.

♻️Reusability

The same backend/data tier can serve multiple frontends — a web app and a mobile app both calling the same APIs.

2-Tier vs 3-Tier vs N-Tier

ModelStructureTrade-off
2-TierClient talks directly to the database (client-server). Simple, but the client is tightly coupled to the DB — hard to scale/secure.
3-TierPresentation → Application → Data, each on its own server/service.Standard cloud-web-app pattern — good balance of scalability, security, maintainability.
N-Tier3-tier further split — e.g. separate API gateway, multiple microservices, caching tier, CDN tier.Maximum flexibility/scalability, but more operational complexity to manage.

Cloud fit: a typical 3-tier web app on AWS looks like CloudFront/CDN → Load Balancer → EC2/App Servers (app tier) → RDS/DynamoDB (data tier) — each tier auto-scales and fails over independently.

07 · Who actually builds this stack EXAM SCOPE

Study of Cloud Tools & Platforms

A survey of the major commercial and open-source platforms/tools used to build, deploy, and manage cloud applications — grouped by what problem each one solves.

Major public cloud providers (IaaS/PaaS/SaaS all-in-one)

🟧AWS (Amazon Web Services)

Market leader — EC2 (compute), S3 (storage), RDS/DynamoDB (databases), Lambda (serverless).

🔵Microsoft Azure

Strong enterprise/hybrid- cloud integration — Azure VMs, Blob Storage, Azure SQL, Azure Functions.

🔴Google Cloud Platform (GCP)

Strong in data/ML — Compute Engine, Cloud Storage, BigQuery, Cloud Functions.

Open-source cloud implementation platforms

🌐OpenStack

Open-source IaaS platform for building private/public clouds — modular services for compute (Nova), storage (Swift/Cinder), networking (Neutron), identity (Keystone).

🐝Eucalyptus / OpenNebula

Earlier open- source private-cloud platforms, AWS-API-compatible (Eucalyptus) — let organizations run "AWS-like" infrastructure on their own hardware.

Virtualization & container tools

🐳Docker

Packages an app + its dependencies into a lightweight, portable container image.

☸️Kubernetes

Orchestrates, auto-scales, and self-heals fleets of containers across a cluster.

🖥️Xen / KVM / VMware

Hypervisors that create the VMs underneath every IaaS offering (see Unit 2).

Infrastructure-as-Code & automation

📜Terraform

Declarative, cloud-agnostic infrastructure provisioning — define infra in code, apply it identically across AWS/Azure/GCP.

🔁Ansible / Chef / Puppet

Configuration- management tools that automate server setup, application deployment, and ongoing config drift.

Cloud programming / simulation tools (for hands-on labs)

CloudSim (simulation)Amazon EC2 / AWS CLIGoogle Colab Postman (API testing)GitHub Actions (CI/CD)
