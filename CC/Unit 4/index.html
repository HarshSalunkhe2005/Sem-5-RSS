01 · Why protecting the cloud is a different problem EXAM SCOPE

Introduction to Cloud Security

Cloud security is the set of policies, technologies, controls and procedures used to protect cloud-hosted data, applications and infrastructure from threats, leaks and unauthorised access. The goal is the same as traditional IT security, but the environment is not: resources are shared, internet-facing, API-driven and spun up in minutes.

Why cloud security differs from traditional (on-premises) security

AspectTraditional / on-premisesCloud
PerimeterClear network boundary (firewall at the edge)Perimeter is blurred — services are internet-reachable; identity becomes the new perimeter
ControlOrganisation owns and controls all layersControl is split with the provider (shared responsibility)
InfrastructureDedicated hardwareMulti-tenant, shared, virtualised
Change speedSlow, planned provisioningResources created/destroyed in minutes via API — config mistakes spread fast
VisibilityFull view of physical networkLimited to what the provider exposes (logs, APIs)
Scale of impactLocal to one environmentOne mistake (e.g. a public storage bucket) can expose huge data

The CIA Triad — the three goals of security

🤐Confidentiality

Only authorised parties can read the data. Achieved by: encryption, access control, authentication.

✅Integrity

Data stays accurate and unaltered by unauthorised parties. Achieved by: hashing, digital signatures, versioning, audit logs.

🟢Availability

Data and services are accessible when needed. Achieved by: redundancy, backups, load balancing, DDoS protection.

Related terms: Authentication (who are you?) → Authorisation (what may you do?) → Accountability / Auditing (what did you do?).

Key cloud security threats

ThreatWhat it isTypical cause / example
Data breachUnauthorised access to / disclosure of sensitive dataStolen credentials, unencrypted data, exposed storage
MisconfigurationWrongly set cloud settings leaving resources exposedPublic storage bucket, open ports, over-permissive roles, default settings

Exam tip: most real-world cloud incidents trace back to misconfiguration and weak identity management, not to the provider's infrastructure being "hacked" — this motivates CSPM and SSO/IAM later in the unit.

02 · Who secures what EXAM SCOPE · high-yield

Shared Responsibility Model

The Shared Responsibility Model divides security duties between the cloud provider and the customer. Short form: the provider secures the cloud itself ("security of the cloud"); the customer secures what they put in it ("security in the cloud"). The more the provider manages (IaaS → PaaS → SaaS), the less the customer is responsible for — but the customer is always responsible for their data and who can access it.

Exact boundaries vary slightly by provider and service — learn the pattern: responsibility shifts towards the provider as you move IaaS → PaaS → SaaS, while data and identity stay with the customer.

03 · The defensive toolkit EXAM SCOPE

Core Cloud Security Controls

A layered ("defence in depth") approach: identity, data, network, visibility, resilience and governance each add an independent line of defence.

🪪Identity & Access Management (IAM)

Controls who can do what on which resource.

  • Least privilege — grant only the minimum permissions needed, nothing more.
  • RBAC (Role-Based Access Control) — permissions attach to roles (e.g. Admin, Developer, Auditor); users get roles.
  • MFA — a second factor (app code, hardware key, biometric) on top of the password.
  • Also: rotate/avoid long-lived keys, separate admin accounts, regular access reviews.

🔒Encryption & Key Management

  • At rest — data stored on disks/DBs/object storage is encrypted (e.g. AES-256).
  • In transit — data moving over networks is encrypted with TLS/HTTPS or VPN.
  • Keys — managed by a KMS (Key Management Service): create, store, rotate, audit and revoke keys; keep keys separate from data.
  • Option: customer-managed keys for more control.

🌐Network Security

  • VPC (Virtual Private Cloud) — logically isolated private network; use public/private subnets.
  • Security groups / NACLs — virtual firewalls allowing only needed ports/IPs.
  • Firewalls — filter traffic at network level.
  • WAF (Web Application Firewall) — protects web apps from SQL injection, XSS and similar HTTP-level attacks.
  • Also: DDoS protection, VPN / private connectivity, network segmentation.

📡Monitoring & Logging

  • Record API calls, logins and configuration changes (audit trail).
  • Collect logs centrally; keep them tamper-resistant.
  • Alert on anomalies (odd logins, privilege changes, traffic spikes); feed a SIEM / security monitoring tool.
  • Enables detection, investigation (forensics) and compliance evidence.

💾Backup & Disaster Recovery

  • Regular, tested backups; keep copies in another region/zone.
  • Define RPO (how much data loss is tolerable) and RTO (how fast service must be restored).
  • Protects availability against deletion, ransomware and outages.

📜Compliance & Governance

Meeting legal/industry standards and proving it with audits and reports. Examples (names only):

ISO/IEC 27001GDPRSOC 2HIPAAPCI DSS

Provider certifications help, but the customer remains responsible for compliant use.

04 · Continuously checking that the cloud is configured safely EXAM SCOPE · syllabus topic

Cloud Security Posture Management (CSPM)

What is CSPM?

CSPM is a category of security tooling that continuously discovers cloud resources, checks their configuration against security best practices and compliance standards, detects misconfigurations and risks, and helps fix them — across one or many cloud accounts. "Posture" = the overall security state/configuration health of your cloud environment.

Why is it needed?

  • Misconfiguration is among the top causes of cloud breaches (public storage, open ports, over-permissive roles, disabled logging/encryption).
  • Cloud is dynamic — resources change constantly; manual review cannot keep up.
  • Multi-cloud / multi-account sprawl — no single place to see risk.
  • Need for continuous compliance evidence instead of one-off audits.
  • Under the shared responsibility model, configuration is the customer's job.

↻ Repeats continuously — CSPM is ongoing monitoring, not a one-time scan.

  1. Discover — connect to cloud accounts (via read-only API access) and build an inventory of assets.
  2. Assess — evaluate settings against policies and benchmarks such as CIS Benchmarks and regulatory frameworks.
  3. Detect drift & risks — spot misconfigurations and configuration drift (a resource changing away from its approved secure baseline).
  4. Prioritise — rank findings by severity, exposure and business context so teams fix what matters first.
  5. Alert / auto-remediate — raise tickets/alerts or automatically correct safe issues (e.g. re-block a public bucket).
  6. Compliance reporting — produce dashboards and reports showing posture against standards.

Key features

🔍 Asset discovery & inventory

Continuous visibility across accounts/clouds.

📏 Policy & benchmark checks

CIS and custom rules for misconfiguration detection.

🔄 Drift detection

Alerts when resources deviate from baseline.

⚠️ Risk prioritisation

Severity scoring, attack-path/exposure context.

🛠️ Remediation

Guided fix steps or automated corrective actions.

📑 Compliance reporting

Mapped to ISO 27001, GDPR, SOC 2 style frameworks.

✅ Benefits

  • Fewer misconfiguration-driven breaches
  • Single view across multi-cloud
  • Faster detection and fixing
  • Continuous (audit-ready) compliance
  • Less manual effort; supports DevSecOps

⚠️ Limitations

  • Focuses on configuration, not live runtime threats or workload contents
  • Can generate many alerts / false positives without tuning
  • Auto-remediation can disrupt services if misapplied
  • Needs broad read access to accounts — must itself be secured
  • Only as good as its policies; a tool, not a replacement for process and skills

05 · One login, many applications EXAM SCOPE · syllabus topic

SSO — Single Sign-On Authentication

Definition

Single Sign-On (SSO) is an authentication scheme that lets a user log in once with one set of credentials and then access multiple independent applications/services without logging in again for each one.

Problem it solves

  • Password sprawl / fatigue — users juggling many passwords reuse weak ones or write them down.
  • Frequent help-desk resets and productivity loss from repeated logins.
  • Scattered, inconsistent identity management — hard to on-board / off-board users everywhere.

Actors

🙋User (Principal)

The person trying to access an application via a browser or client.

🏛️Identity Provider (IdP)

Central trusted system that authenticates the user and issues proof (assertion/token). e.g. corporate directory login service.

🧩Service Provider (SP)

The application/service the user wants; it trusts the IdP instead of keeping its own password.

How SSO login works (step by step)

SSO flow — user, service provider, identity provider

Userbrowser
Service Provider (SP)application
Identity Provider (IdP)login authority
1 → Request access to the application
2 ← No session: redirect user to the IdP
3 → Browser reaches IdP; user logs in (password + MFA)
4 ← IdP authenticates; issues token / assertion
5 → Browser presents token to the SP
6 ← SP validates token (trust in IdP) and grants access
7 → Later: another app redirects to IdP; existing session reused — no new login
  1. User tries to open an application (SP).
  2. SP finds no valid session and redirects the user to the IdP.
  3. User authenticates at the IdP (password, preferably + MFA).
  4. IdP creates a session and issues a signed token/assertion proving identity.
  5. User's browser sends the token to the SP.
  6. SP verifies the signature and grants access.
  7. When the user opens a second app, the IdP sees the existing session and issues a token without asking for credentials again.

SSO protocols & standards

ProtocolOne-line explanationTypical use
SAML 2.0XML-based standard exchanging signed authentication/authorisation assertions between IdP and SP.Enterprise / workforce web SSO
OAuth 2.0An authorisation framework: lets an app get limited access to resources on a user's behalf via access tokens, without sharing the password.API access, "allow this app to read your calendar"
OpenID Connect (OIDC)An authentication layer built on top of OAuth 2.0; adds an ID token (JWT) that says who the user is.Modern web/mobile "Sign in with …" SSO
KerberosTicket-based network authentication using a trusted key distribution centre; user gets tickets instead of sending passwords.Enterprise/intranet (e.g. Windows domains)

Classic exam trap: OAuth 2.0 = authorisation (what an app may access). OpenID Connect = authentication (who the user is), built on OAuth 2.0. SAML does both in the XML/enterprise world.

Federation (federated identity)

Federation extends SSO across organisational or domain boundaries: separate organisations establish trust so a user authenticated by their home IdP can access a partner's or a cloud provider's services without a separate account. Example: logging in to a cloud service or partner portal with your organisation's credentials. SAML and OIDC are the usual federation protocols.

SSO + MFA

Because one login unlocks many applications, the IdP login must be strong. Combining SSO with MFA (password + one-time code/hardware key/biometric) protects every connected app at once. Adaptive/risk-based policies can demand extra verification only for unusual logins.

Benefits vs risks

✅ Benefits

  • Better user experience; fewer passwords to remember
  • Fewer weak/reused passwords and phishing surfaces
  • Lower help-desk/password-reset cost
  • Centralised policy, auditing and quick user de-provisioning
  • Easy enforcement of MFA

⚠️ Risks

  • Single point of failure — if the IdP is down, users can't reach any app
  • Single point of compromise — stolen SSO credentials expose all connected apps
  • Integration effort; legacy apps may not support SSO
  • Misconfigured trust/tokens can be exploited

Best practices

  • Enforce MFA on the IdP (especially for admins).
  • Make the IdP highly available (redundancy) and have an emergency "break-glass" admin access.
  • Use short token lifetimes, secure session handling and signed/validated tokens.
  • Apply least privilege / RBAC on top of SSO; review access regularly.
  • Log and monitor authentication events; alert on anomalies.
  • Use modern protocols (OIDC/SAML) rather than custom schemes; automate de-provisioning on exit.

Likely exam questions with model answers

Q1. What is cloud security? Explain the CIA triad.

Cloud security is the set of policies, technologies and controls that protect cloud-hosted data, applications and infrastructure from threats and unauthorised access. CIA: Confidentiality (only authorised access, via encryption/access control), Integrity (data not altered without authorisation, via hashing/signatures/logs), Availability (data and services accessible when needed, via redundancy/backups/DDoS protection).

Q2. List and explain major cloud security threats.

Data breaches (unauthorised data exposure); misconfiguration (e.g. public storage, open ports); insecure APIs; account hijacking (phishing, stolen keys); insider threats; DDoS (denial of availability); data loss (deletion, ransomware); shared-technology vulnerabilities (weak tenant isolation). Misconfiguration and weak identity management are the most common practical causes.

Q3. Explain the Shared Responsibility Model across IaaS, PaaS and SaaS.

The provider secures the underlying cloud (facilities, hardware, network, hypervisor); the customer secures what they deploy and configure. In IaaS the customer also manages OS, middleware, apps, network config, data and access; in PaaS the provider also manages OS/runtime, customer handles code, data, access; in SaaS the provider manages almost everything and the customer handles data, user access and app settings. Data and identity are always the customer's responsibility.

Q4. Describe the core security controls used in the cloud.

IAM with least privilege, RBAC and MFA; encryption at rest and in transit with keys managed in a KMS; network security via VPC, security groups, firewalls and WAF; monitoring and logging for detection and audit; backup and disaster recovery for availability; and compliance with standards such as ISO 27001, GDPR and SOC 2.

Q5. What is CSPM? Why is it needed and how does it work?

CSPM continuously discovers cloud assets, checks configurations against benchmarks (e.g. CIS) and policies, detects misconfigurations and drift, prioritises risks, alerts or auto-remediates, and reports compliance. It is needed because misconfigurations are a leading cause of cloud breaches and manual checking can't keep pace with dynamic, multi-cloud environments.

Q6. Differentiate CSPM, CWPP and CASB.

CSPM secures cloud configuration (posture, compliance, drift). CWPP protects workloads such as VMs, containers and serverless (vulnerabilities, runtime protection). CASB sits between users and cloud/SaaS services to give visibility, DLP and access control over cloud usage. They are complementary.

Q7. What is SSO? Explain its working with the roles involved.

SSO lets a user authenticate once and access multiple applications without re-entering credentials. Roles: user, Identity Provider (authenticates and issues a token) and Service Provider (trusts the IdP). Flow: user requests app → SP redirects to IdP → user logs in (+MFA) → IdP issues signed token → user presents it to SP → SP validates and grants access; later apps reuse the IdP session.

Q8. Compare SAML, OAuth 2.0 and OpenID Connect. What are SSO's advantages and risks?

SAML: XML assertions for enterprise web SSO. OAuth 2.0: authorisation framework (delegated access via access tokens, not authentication). OIDC: authentication layer on OAuth 2.0 providing an ID token about the user. Advantages: fewer passwords, better UX, centralised control, easy MFA and de-provisioning. Risks: the IdP is a single point of failure and compromise — mitigate with MFA, high availability, short-lived tokens and monitoring.
