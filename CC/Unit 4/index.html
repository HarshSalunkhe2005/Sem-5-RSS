01 · Why protecting the cloud is a different problem EXAM SCOPE

Introduction to Cloud Security

The deck is organised in three modules: Module 1 Introduction to Cloud Security, Module 2 Cloud Security Posture Management (CSPM), Module 3 Single Sign-On (SSO). Its learning outcomes: assign a control to customer or provider for IaaS/PaaS/SaaS; explain why misconfiguration is the leading cause of cloud breaches and how CSPM detects it; distinguish CSPM from CWPP, CIEM, KSPM and CNAPP; trace how SAML, OAuth 2.0 and OpenID Connect move a user from "not logged in" to "authenticated"; and identify SSO risks and mitigations.

Recap: service and deployment models

Cloud computing is the on-demand delivery of computing resources — servers, storage, databases, networking, software — over the internet, billed on a pay-as-you-go basis instead of being bought and run in a private data centre.

🖥️IaaS

Provider gives raw virtual machines, storage and networking; you install and manage everything above that. Example: Amazon EC2, Azure Virtual Machines.

🧱PaaS

Provider also manages the operating system and runtime; you deploy application code. Example: AWS Elastic Beanstalk, Azure App Service, Google App Engine.

📦SaaS

Provider runs the entire application; you just use it via browser or app. Example: Salesforce, Zoom, Microsoft 365, Workday.

Public cloud

Shared infrastructure, e.g. AWS, Azure, GCP.

Private cloud

Dedicated to one organisation; common in large banks handling regulated data.

Hybrid cloud

A mix of both — how most large Indian enterprises (including many banks and NBFCs) operate: sensitive core-banking data stays on-premises or in a private cloud, customer-facing apps and analytics run on public cloud.

Example: a food-delivery app such as Swiggy likely runs on IaaS/PaaS (virtual machines or managed container services), stores order history in a managed database (PaaS) and uses SaaS tools internally for support ticketing or analytics dashboards — one company routinely uses all three service models at once.

Why cloud security is a different discipline

Traditional security assumed a fixed perimeter: servers in your own data centre, behind your own firewall, where "inside" meant "trusted". The cloud dissolves that perimeter: the database may sit in a data centre you have never seen, traffic may cross the public internet between microservices, and one misclicked checkbox in a web console can expose data to the whole internet in seconds. Three shifts:

🤝Shared control

You no longer control every layer of the stack — some is the provider's job, some yours, and the split changes across IaaS, PaaS and SaaS.

⚡Speed and scale

Infrastructure is created and destroyed through code (Infrastructure as Code) in seconds. One engineer can accidentally provision thousands of insecure resources before anyone notices — impossible in a hardware data centre.

🔌API-driven everything

Every resource is reachable and configurable through an API. Powerful, but a leaked API key or an over-permissioned identity can do as much damage as a stolen physical server key.

The CIA Triad in the cloud

The classic Confidentiality, Integrity, Availability triad still anchors cloud security, but each pillar takes on a cloud-specific flavour:

PillarTraditional meaningCloud-specific concern

Beyond the deck Typical safeguards: confidentiality — encryption, access control, authentication; integrity — hashing, digital signatures, versioning, audit logs; availability — redundancy, backups, load balancing, DDoS protection. Related terms: Authentication (who are you?) → Authorisation (what may you do?) → Accountability / Auditing (what did you do?).

The cloud security threat landscape (six categories)

Six categories recur in almost every publicly documented cloud breach of the last decade:

CategoryWhat it means / example
1. MisconfigurationA setting left in its default or overly permissive state — a storage bucket set to "public", a database reachable from the open internet, an admin console with no MFA. Not a sophisticated attack; needs no hacking skill, which is why it is so common and damaging.
2. Weak identityOver-permissioned identities and weak access control — an over-permissioned identity can do as much damage as a stolen server key.
3. Insecure APIsEvery cloud resource is managed through APIs, so a leaked API key lets an attacker act on the account.
4. Data exposurePublic buckets and over-shared links leaving data readable by people who should not see it.
5. Account hijackingIncreasingly targets session tokens rather than passwords — relevant to SSO, since a stolen SSO session token can be as dangerous as a password, sometimes more, because it may bypass login and MFA entirely.
6. Availability attacksDDoS against public endpoints, accidental deletion by automation, regional outages.

Beyond the deck Other threats often listed in textbooks:

ThreatWhat it is
Insider threatMalicious or careless employee/contractor misuses access (excess privileges, accidental deletion).
Data lossPermanent loss of data through deletion, ransomware, provider failure or no backups.
Shared-technology issuesWeakness in multi-tenant shared components (hypervisor, shared hardware) affecting tenant isolation.

Exam tip: misconfiguration, not sophisticated hacking, is the leading cause of cloud data breaches — real incidents trace back to misconfiguration and weak identity management, not the provider's infrastructure being "hacked". This motivates CSPM and SSO/IAM later in the unit.

02 · Who secures what EXAM SCOPE · high-yield

Shared Responsibility Model

The Shared Responsibility Model is the most important mental model in cloud security. Every major provider (AWS, Microsoft Azure, Google Cloud) publishes a version, and most incidents trace back to someone misunderstanding where the line sits. Short form: the provider secures the cloud itself ("security of the cloud"); the customer secures what they put in it ("security in the cloud").

  • Provider — security OF the cloud: physical data centres, host hardware, the virtualisation layer and (depending on the service) the underlying network.
  • Customer — security IN the cloud: how they configure identity and access, how they classify and protect data, how they configure applications and networks.
  • As you move IaaS → PaaS → SaaS the provider takes on more of the stack, but the customer's responsibility for data and identity & access management never goes away.

Common misunderstanding: "we're on SaaS, so security is the vendor's problem" is a sentence that has caused real breaches.

Example: same provider, different responsibility

On AWS, if you run your application on an EC2 virtual machine (IaaS), you patch the operating system. If you run the same code on AWS Lambda (serverless / PaaS-like), AWS patches the underlying OS — but you are still 100% responsible for what your code does with the data and for who is allowed to invoke the function.

Case study: the Capital One breach (2019)

Capital One, a major US bank running on AWS, suffered a breach affecting over 100 million customer records (credit scores, balances, Social Security numbers).

  • Root cause was not a flaw in AWS infrastructure. A former employee of a third-party firm exploited a misconfigured Web Application Firewall (WAF) that Capital One's own team had set up.
  • The WAF had excessive permissions and could be tricked into requesting temporary security credentials from the instance metadata service, which were then used to list and read data from Capital One's own S3 buckets.
  • AWS secured "the cloud" as promised; the customer-side misconfiguration on the customer's side of the shared-responsibility line caused the breach.

The canonical teaching example for shared responsibility, and exactly the class of problem CSPM (Module 2) catches automatically and continuously, before an attacker finds it. Keep it as your standard "one real breach" example for interviews/exams.

03 · The defensive toolkit EXAM SCOPE

Core Cloud Security Controls

A cloud security program rests on five interlocking pillars. The course goes deep on identity (via SSO) and posture (via CSPM), but you should be fluent in all five.

1Identity & Access Management (IAM)

Who can do what, enforced through the principle of least privilege — grant only the permissions actually required, nothing more.

Example: Amazon's IAM lets a retail platform allow its "order processing" microservice to read the orders table — and explicitly deny it access to the payments table.

2Data Protection

Encryption at rest (data in storage) and in transit (data moving across the network), tokenization of sensitive fields such as card numbers, and data classification so teams know what is sensitive.

3Network Security

Virtual Private Clouds (VPCs), security groups and firewall rules, and segmentation so a compromised front-end service cannot directly reach a payments database.

4Compliance & Governance

Mapping technical controls to frameworks and regulations: ISO 27001, PCI-DSS (payment card data) and, in India, the RBI IT framework for banks and the Digital Personal Data Protection (DPDP) Act.

5Monitoring, Detection & Response

Logging, alerting and the continuous posture-checking that Module 2 (CSPM) covers in depth.

Control details Beyond the deck

The cards below expand the pillars with standard textbook detail that the deck does not spell out.

🪪IAM in more detail

  • RBAC (Role-Based Access Control) — permissions attach to roles (Admin, Developer, Auditor); users get roles.
  • MFA — a second factor (app code, hardware key, biometric) on top of the password.
  • Rotate/avoid long-lived keys, separate admin accounts, regular access reviews.

🔒Encryption & key management

  • At rest e.g. AES-256; in transit with TLS/HTTPS or VPN.
  • KMS (Key Management Service) creates, stores, rotates, audits and revokes keys; keep keys separate from data.
  • Option: customer-managed keys for more control.

🌐Network extras

  • NACLs as subnet-level firewalls; public/private subnets.
  • WAF protects web apps from SQL injection, XSS and similar HTTP-level attacks.
  • DDoS protection, VPN / private connectivity.

📡Monitoring extras

  • Record API calls, logins and configuration changes (audit trail); keep logs tamper-resistant.
  • Feed a SIEM / security monitoring tool; enables forensics and compliance evidence.

💾Backup & disaster recovery

  • Regular, tested backups; keep copies in another region/zone.
  • RPO (tolerable data loss) and RTO (time to restore service).
  • Protects availability against deletion, ransomware and outages.

04 · Continuously checking that the cloud is configured safely EXAM SCOPE · syllabus topic

Cloud Security Posture Management (CSPM)

Why CSPM exists: the misconfiguration problem

Industry breach reports year after year identify misconfigured cloud resources — open storage, overly permissive firewall rules, disabled logging, unencrypted databases exposed to the internet — as the single largest root cause. Three forces make this worse at scale and mean manual review can never keep up:

📊 Volume

A mid-size company can easily run tens of thousands of cloud resources across multiple accounts, regions and providers.

⚡ Velocity

Infrastructure as Code and CI/CD pipelines create and change resources continuously, all day, by many engineers.

🌊 Drift

A resource configured correctly on Monday can be manually "fixed" by an engineer under pressure on Friday in a way that quietly reopens a gap — with nobody re-reviewing it.

What is CSPM? (formal definition)

Cloud Security Posture Management (CSPM) is a category of security tooling that continuously and automatically discovers cloud resources, evaluates their configuration against security best practices and compliance frameworks, and surfaces — or automatically fixes — any misconfiguration or policy violation it finds, across every cloud account an organisation owns. "Posture" = the overall security state/configuration health of the cloud environment.

Three words matter most: continuously (not a one-time audit), automatically (not a human clicking through consoles) and every account (most organisations are multi-cloud or multi-account, and a visibility gap is itself a security gap).

How a CSPM platform works

Every CSPM platform, cloud-native or third-party, follows the same architecture: it connects to your cloud accounts using read-only API credentials, builds a live inventory of every resource, evaluates it against a policy library, and pushes prioritised findings to the teams and tools that act on them.

CSPM is agentless: it installs nothing inside your VMs or containers; it reads configuration through the provider's management APIs — the same APIs a console user or an Infrastructure-as-Code tool would use. This is the key distinction from CWPP, which does run inside the workload.

The continuous cloud security cycle (5 stages)

CSPM is not a report generated once a quarter for an audit — it is a closed loop that runs continuously.

↻ Repeats continuously — CSPM is ongoing monitoring, not a one-time scan.

  1. Discover — build and maintain a live inventory of every account, service and asset, including "shadow" resources an engineer spun up without telling anyone.
  2. Assess — check each resource's configuration against rules derived from the CIS Benchmarks, PCI-DSS and ISO 27001, plus custom organisational rules.
  3. Prioritise — not every finding is equally urgent: a public bucket holding customer PII is a five-alarm fire; an unused test resource with a minor issue is not. Good tools rank by exploitability and business impact, not raw count.
  4. Remediate — fix automatically (well-understood, low-risk fixes) or route a clear, actionable ticket to the owning team, ideally with a one-click fix or a ready-made Infrastructure-as-Code pull request.
  5. Monitor — watch continuously for new resources and new configuration drift, and start the loop again.

Example — multi-cloud reality: a fast-growing company like Lenskart or Flipkart, with many engineering teams, often runs workloads across more than one provider plus many SaaS tools. A third-party CSPM tool with one unified view is frequently more valuable than any single provider's native tool, because it removes the blind spots between providers.

Case study: anatomy of an exposed storage bucket (composite scenario)

  1. A large e-commerce marketing team must share product images with an external agency. An engineer creates a storage bucket and, to avoid access-request back-and-forth, sets it to "public read". It is never revisited.
  2. Eighteen months later another internal team reuses the same bucket to stage a nightly analytics export — a CSV with partial customer order data — "just for a few hours". The public-read policy is still set.
  3. Internet scanners that continuously sweep the public cloud IP space find the file within hours.

The pattern — opened for a narrow legitimate reason, never re-locked, then reused for something more sensitive — mirrors a large share of publicly reported cloud storage exposures. A CSPM tool would have flagged "public read" the moment it was set, and again every day it stayed public, regardless of what was later placed inside.

Case study: multi-cloud posture at hyper-growth scale

In a hyper-growth consumer platform (Lenskart or a food-delivery unicorn), engineering teams multiply fast, each with autonomy to ship, and backend services move to containers orchestrated with Kubernetes across multiple regions and sometimes multiple providers. CSPM's job extends naturally into KSPM:

  • Kubernetes cluster API servers must not be exposed to the public internet.
  • Pod security policies must prevent containers running with excessive privileges.
  • RBAC inside the cluster must follow least privilege.

Same philosophy as classic CSPM, applied one layer deeper in the stack.

05 · One login, many applications EXAM SCOPE · syllabus topic

SSO — Single Sign-On Authentication

The problem: password fatigue

A typical smartphone user in India uses Swiggy or Zomato, Flipkart or Amazon, Lenskart, a net-banking app, a UPI app, a workplace email account and more in a single week. If each needed its own unique strong password, people either reuse the same password everywhere (one leak compromises many accounts) or lean on the "forgot password" flow so often it becomes a support burden. Security teams call this password fatigue — the human problem SSO exists to solve.

Definition

Single Sign-On (SSO) is an authentication scheme that lets a user log in once with one set of credentials and then access multiple independent applications/services without logging in again for each one.

Without SSO vs with SSO (deck Figure 3.1)

Without SSOUser ↔ App 1, App 2, App 3 — one password per app
vs
With SSOUser → one trusted Identity Provider, which vouches for the user to every app

You already use SSO constantly: every "Continue with Google" or "Continue with Facebook" tap, or every time your office laptop logs you into email, chat and the HR portal without asking again.

Core actors

🙋User

The human trying to log in.

🏛️Identity Provider (IdP)

Trusted system that actually verifies who the user is (checks password, sends OTP, enforces MFA) and issues signed proof of identity. e.g. Google, Microsoft Entra ID (formerly Azure AD), Okta, a bank's own authentication server.

🧩Service Provider (SP) / Relying Party

The application the user wants; it trusts the IdP's word instead of checking the password itself. e.g. Workday, Salesforce, a food-delivery app accepting "Sign in with Google".

The whole security value of SSO rests on one decision: the Service Provider never sees or handles the user's actual password. It only receives a signed statement from the IdP: "I have verified this user; here is proof."

Authentication vs authorization

TermQuestion it answersEveryday analogy
Authentication (AuthN)Who are you?Showing your ID card at a building's front desk.
Authorization (AuthZ)What are you allowed to do?The visitor badge that only opens certain floors.

Common mistake: OAuth 2.0 is fundamentally an authorization protocol, not authentication — even though it is widely used as the basis of consumer login. Using raw OAuth 2.0 alone to log a user in (without OpenID Connect on top) is a well-known anti-pattern that has caused real vulnerabilities.

SAML 2.0 — enterprise SSO

Security Assertion Markup Language (SAML) 2.0 is an XML-based standard, published in 2005, and still the dominant protocol for enterprise SSO — the login a bank employee or college administrator uses when one corporate login unlocks email, HR and many internal tools. Its core artifact is the Assertion: a signed XML document stating who the user is and what attributes (department, role, email) are true about them. In the deck's quiz, SAML is an authentication protocol, not primarily authorization.

  2. SP finds no valid session and redirects the user to the IdP.
  3. User authenticates at the IdP (password, preferably + MFA).
  4. IdP issues a signed token/assertion proving identity.

Example — enterprise SAML: a bank configures its corporate IdP (commonly Okta or Microsoft Entra ID) as the single source of truth for employee identity. Opening Salesforce or Workday redirects the employee to the bank's own login page (its password policy and mandatory MFA); only after success do they land inside Salesforce, already signed in. If the employee leaves, disabling the one IdP account instantly revokes access to every connected application — a critical control for compliance and offboarding.

OAuth 2.0 — delegated authorization

OAuth 2.0 solves a different problem: how can a user grant one application limited access to their data on another service, without handing over their password? Classic example: letting a photo-printing website access only your Google Photos library, without giving it your Google password (which would also let it read your Gmail).

OAuth 2.0 Authorization Code flow (deck Figure 3.3) — "Login with Google"

  1. User taps "Continue with Google" inside the app (client).
  2. App redirects the browser to Google's authorization endpoint (/authorize).
  3. User authenticates with Google and approves the specific permissions (scopes) requested.
  4. Google redirects back to the app with a short-lived, single-use authorization code.
  5. Back-channel step: the app exchanges the code for an access token over a secure server-to-server request that also includes the app's own client secret.
  6. Google returns the access token, often with a longer-lived refresh token.
  7. App uses the access token to call Google's API.
  8. Google returns the requested data, which the app uses to create the user's session.

Why the back-channel step matters: step 5 happens server-to-server, not through the user's browser, which keeps the client secret confidential and stops the authorization code being intercepted and reused. Mobile and single-page apps cannot safely store a secret, so they use PKCE (Proof Key for Code Exchange) for the same protection without a stored secret.

OpenID Connect & the JSON Web Token (JWT)

If OAuth 2.0 is about authorization, how does "Login with Google" work as a login? Through OpenID Connect (OIDC) — a thin, standardised identity layer built directly on top of OAuth 2.0. OIDC adds one new artifact to the flow above: a signed ID Token, formatted as a JWT, which makes a verifiable statement about who the user is, not just what data the app may access.

Headersigning algorithm
.

A JWT has three parts separated by dots, each Base64Url-encoded (header.payload.signature). Because the signature can be verified using only the IdP's public key, the receiving app never needs to call the IdP back — it verifies locally, one reason JWT-based OIDC is popular for high-scale consumer apps.

SAML vs OAuth vs OIDC — choosing the protocol

One of the most exam- and interview-relevant comparisons in the unit (deck Figure 3.5):

ProtocolOne-line explanationTypical use
SAML 2.0XML-based standard exchanging signed assertions between IdP and SP; authentication (with attributes) for enterprise SSO.Enterprise / workforce web SSO
OAuth 2.0An authorization framework: lets an app get limited access to resources on a user's behalf via access tokens, without sharing the password.API access, "allow this app to read your photos/calendar"

Rule of thumb: enterprise workforce SSO into business software → SAML (or OIDC, which is increasingly replacing SAML even in enterprises). Only need to call another service's API on a user's behalf → OAuth 2.0. Need to know who the user is (a "Sign in with..." button) → OpenID Connect.

Beyond the deck Kerberos — ticket-based network authentication using a trusted key distribution centre; the user gets tickets instead of sending passwords. Typical use: enterprise/intranet (e.g. Windows domains).

Classic exam trap: OAuth 2.0 = authorization (what an app may access). OpenID Connect = authentication (who the user is), built on OAuth 2.0. SAML is an authentication protocol for enterprise SSO.

Case study: SSO in banking and net-banking

An Indian bank's digital ecosystem has a net-banking portal, a mobile app and UPI integration, plus (for staff) a separate internal SSO layer for email, HR and internal tools. For customer-facing SSO, banks work under tighter constraints than a shopping app:

  • RBI guidelines mandate strong multi-factor authentication for financial transactions.
  • Session tokens are typically extremely short-lived compared to a shopping app.
  • Identity is frequently anchored to the registered mobile number and a device-level trust signal.
  • UPI PIN or biometric verification adds a transaction-level step on top of the initial SSO-style login.

Lesson: SSO establishes who you are once, while sensitive actions can still demand extra targeted re-verification — step-up authentication.

Case study: Lenskart — social login and OTP-based SSO

Consumer platforms like Lenskart offer two low-friction entry points: "Continue with Google" (an OIDC flow, as above) and phone number + OTP, where the platform's own backend acts as the Identity Provider and texts a one-time code to verify the user controls that number. Both are conceptually SSO: the user skips creating a Lenskart-specific password by trusting an already-established identity signal (a Google account, or control of a phone number). The OTP flow needs careful engineering:

  • Rate-limit OTP requests (prevents SMS-bombing abuse).
  • Short OTP expiry windows.
  • Bind OTP verification to the device/session that requested it, so a leaked OTP alone cannot be replayed from an attacker's device.

SSO security risks and mitigations

Centralising authentication concentrates risk: if the single Identity Provider is compromised, every connected application is potentially compromised too.

RiskWhat it isMitigation
Token theft / replayAttacker steals a valid session or access token (malware, compromised network, XSS) and reuses it to impersonate the user.Short token lifetimes; token binding to device/IP where feasible; secure (HttpOnly, encrypted) token storage.
SAML XML signature wrappingManipulates the structure of a signed SAML XML message so a signature valid for one part appears to validate a maliciously altered part.Well-maintained, standards-compliant SAML libraries rather than custom XML parsing; strict schema validation.
Open redirectA poorly validated redirect parameter sends the user's browser (sometimes their auth code) to an attacker-controlled site after login.Strict allow-lists of valid redirect URIs registered in advance with the IdP.
Phishing via consent screensA malicious app registers with an IdP and tricks users into approving broad OAuth scopes.IdP-side app vetting/verification; users reviewing requested scopes; minimal scope requests by legitimate apps.
Session fixationAttacker forces a victim to use a session identifier the attacker already knows, then hijacks the session after the victim authenticates.Always issue a brand-new session identifier immediately after successful authentication.

SSO + MFA: stronger together

SSO and Multi-Factor Authentication (MFA) solve different problems. SSO reduces how many passwords exist to attack; MFA makes each authentication event harder to defeat even if the first factor is compromised, by requiring a second independent proof — something the user has (phone, hardware key) or something the user is (fingerprint, face). They are complementary, not redundant.

Key point: SSO centralises authentication into one IdP, making it the single highest-value target in the system. Enforcing MFA at the IdP is therefore one of the highest-leverage controls — it protects every connected application at once. Many modern IdPs also support adaptive / risk-based authentication, prompting for a second factor only when a login looks unusual (new device, new country, impossible travel time).

Federation, benefits, risks and best practices Beyond the deck

Federation extends SSO across organisational or domain boundaries: separate organisations establish trust so a user authenticated by their home IdP can access a partner's or cloud provider's services without a separate account. SAML and OIDC are the usual federation protocols.

✅ Benefits

  • Better user experience; fewer passwords to remember
  • Fewer weak/reused passwords and phishing surfaces
  • Lower help-desk/password-reset cost
  • Centralised policy, auditing and quick de-provisioning
  • Easy enforcement of MFA

⚠️ Risks

  • Single point of failure — if the IdP is down, users can't reach any app
  • Single point of compromise — stolen SSO credentials expose all connected apps
  • Integration effort; legacy apps may not support SSO
  • Misconfigured trust/tokens can be exploited
  • Enforce MFA on the IdP (especially for admins); make the IdP highly available with an emergency "break-glass" admin access.
  • Use short token lifetimes, secure session handling and signed/validated tokens.
  • Apply least privilege / RBAC on top of SSO; review access regularly; log and monitor authentication events.
  • Use modern protocols (OIDC/SAML) rather than custom schemes; automate de-provisioning on exit.

Likely exam questions with model answers

Q1. What is cloud security? Explain the CIA triad in the cloud.

Cloud security protects cloud-hosted data, applications and infrastructure from threats and unauthorised access; the perimeter dissolves, control is shared, resources are created by code in seconds and everything is API-driven. Confidentiality: only authorised people see data (cloud risks: public buckets, over-shared links, cross-tenant leakage). Integrity: data isn't tampered with (unauthorised IaC changes, unsigned API calls, container-image supply-chain tampering). Availability: systems stay up (DDoS, accidental deletion by automation, regional outages).

Q2. List and explain the six categories of cloud security threat.

Misconfiguration (default/overly permissive settings such as a public bucket — needs no hacking skill); weak identity (over-permissioned identities); insecure APIs (leaked keys act on the account); data exposure (public buckets, over-shared links); account hijacking (increasingly via session tokens, which can bypass login and MFA); availability attacks (DDoS, accidental deletion, outages). Misconfiguration and weak identity management are the most common practical causes.

Q3. Explain the Shared Responsibility Model across IaaS, PaaS and SaaS. Use the Capital One breach as an example.

Provider = security of the cloud (data centres, host hardware, virtualisation layer, sometimes the network); customer = security in the cloud (identity and access, data classification and protection, application and network configuration). Moving IaaS → SaaS the provider takes more of the stack, but data and IAM stay with the customer. E.g. on EC2 you patch the OS; on Lambda AWS does, but you still own what the code does with data. In the 2019 Capital One breach (100M+ records) a misconfigured WAF with excess permissions was tricked into fetching temporary credentials from the instance metadata service, used to read S3 buckets — a customer-side failure, not an AWS flaw.

Q4. Name the five pillars of a cloud security program.

(1) IAM — who can do what, via least privilege; (2) Data protection — encryption at rest and in transit, tokenization, data classification; (3) Network security — VPCs, security groups/firewall rules, segmentation; (4) Compliance & governance — ISO 27001, PCI-DSS, RBI IT framework, DPDP Act; (5) Monitoring, detection & response — logging, alerting, continuous posture checking.

Q5. What is CSPM? Why is it needed and how does it work?

CSPM continuously and automatically discovers cloud resources, evaluates their configuration against best practices and compliance frameworks, and surfaces or fixes misconfigurations across every account. Needed because misconfiguration is the leading breach cause and manual review fails under volume, velocity and drift. It connects with read-only API credentials (agentless), builds a live inventory, checks it against a policy library and runs a 5-stage loop: Discover → Assess (CIS, PCI-DSS, ISO 27001, custom rules) → Prioritise (exploitability and business impact) → Remediate (auto-fix, ticket, IaC pull request) → Monitor.

Q6. Differentiate CSPM, CWPP, CIEM, KSPM and CNAPP.

CSPM: "is this resource configured securely?" (agentless, via APIs). CWPP: "is this running workload (VM, container, function) behaving securely now?" (runs inside the workload). CIEM: "does this identity have more access than it needs?" KSPM: the CSPM question for Kubernetes clusters, pods and RBAC. CNAPP: the umbrella platform bundling all of them. Beyond the deck CASB additionally governs how users consume cloud/SaaS services.

Q7. What is SSO? Explain its working with the roles involved.

SSO lets a user authenticate once with one set of credentials and access multiple independent applications. Roles: user, Identity Provider (verifies the user, enforces MFA, issues signed proof) and Service Provider / relying party (trusts the IdP and never sees the password). Flow: user opens app → SP redirects to IdP → user authenticates (+MFA) → IdP returns a signed assertion/token → SP verifies the signature and grants access. It solves password fatigue (reuse, constant resets).

Q8. Compare SAML, OAuth 2.0 and OpenID Connect. Which would you use when?

SAML 2.0: XML-based (2005), signed Assertions, dominant in enterprise SSO. OAuth 2.0: delegated authorization — limited access to a user's data via access tokens without sharing the password; NOT authentication. OIDC: identity layer on OAuth 2.0 adding a signed JWT ID Token (header.payload.signature, verified locally with the IdP's public key). Use SAML (or OIDC) for enterprise workforce SSO, OAuth 2.0 to call another service's API on a user's behalf, OIDC for "Sign in with..." login.

Q9. Explain the OAuth 2.0 Authorization Code flow. Why is the back-channel step important and what is PKCE?

User taps "Continue with Google" → app redirects to Google's authorization endpoint → user authenticates and approves scopes → Google redirects back with a short-lived single-use authorization code → app exchanges the code (server-to-server, with its client secret) for an access token → Google returns access token (often plus refresh token) → app calls the API → Google returns data and the app creates the session. The back-channel exchange keeps the secret out of the browser and stops the code being intercepted and reused. Mobile/single-page apps cannot store a secret, so they use PKCE instead.

Q10. Why is OAuth 2.0 alone not an authentication protocol? List common SSO risks and mitigations.

OAuth 2.0 only conveys what an app may access (authorization); it does not carry a verified statement of who the user is, so using it alone for login is an anti-pattern; OIDC adds the signed ID Token. Risks: token theft/replay (short lifetimes, token binding, secure storage); SAML XML signature wrapping (standards-compliant libraries, schema validation); open redirect (allow-listed redirect URIs); consent-screen phishing (app vetting, minimal scopes); session fixation (new session ID after authentication). Enforce MFA at the IdP; use step-up authentication for sensitive actions.

Classroom exercises from the deck, with answers

Exercise 1. Whose responsibility is it? (Provider / Customer / Shared)

1. Patching physical-server firmware → Provider. 2. Setting a storage bucket to private → Customer (configuration choice). 3. Enforcing MFA for admin console logins → Customer (access-control policy, though the MFA capability comes from the vendor). 4. Encrypting customer data before storing it in a managed database → Customer (data protection never fully delegated, even on SaaS). 5. Data-centre backup power and guards → Provider. 6. Configuring which microservices may talk to which inside a VPC → Customer. 7. Patching the hypervisor → Provider (virtualisation layer).

Exercise 2. Spot the misconfiguration: bucket prod-customer-exports has public access allowed (read + list), encryption at rest disabled, access logging disabled, versioning disabled, attached IAM role "AdministratorAccess". Which is most urgent? Which would have reduced impact? Which is a least-privilege violation?

All the settings are problems, but public access on a bucket named "prod-customer-exports" is the most urgent — an active, ongoing data exposure. Enabling encryption at rest would not have prevented discovery but would have reduced the impact if the data were still accessed. The AdministratorAccess role is a distinct least-privilege violation: even resources with no exposure issue should never get broader permissions than they need.

Exercise 3. Map the OAuth login flow (fill the blanks): (1) the user taps "Continue with Google" inside the ____; (2) the app redirects the browser to Google's ____ endpoint; (3) Google returns a short-lived, single-use ____; (4) the app exchanges it for an access token using a ____-channel request; (5) which artifact added by OIDC tells the app the user's identity?

(1) Client app / Service Provider; (2) authorization (/authorize); (3) authorization code; (4) back; (5) the OpenID Connect ID Token (a JWT).

Exercise 4. Rapid-fire true/false.

1. SAML is primarily an authorization protocol — False (authentication). 2. OAuth 2.0 alone is sufficient and safe for logging a user in — False (use OIDC). 3. A JWT's signature can be verified without calling the IdP back — True. 4. In SSO the Service Provider directly checks the user's password — False (the IdP does). 5. MFA and SSO solve the same problem and are redundant together — False (complementary). 6. PKCE exists because mobile/single-page apps cannot safely store a client secret — True.
