01 · Where it came from

Origins of Cloud Computing

Cloud computing didn't appear out of nowhere — it's the third stage of an evolution in how computing resources are shared:

🖥️Client-Server

All data and control sits on a central server. A client must connect to the server first, then gets access. Simple, but the server is a single point of failure and doesn't scale well.

🔗Distributed Computing

Multiple computers are networked together and share resources with each other. Better resource sharing, but still has real limitations in coordination and management.

☁️Cloud Computing

Emerged specifically to remove the limitations of distributed computing — centralized, elastic, on-demand resource pooling accessible over the internet.

Key historical milestones

1961
John McCarthy (MIT): "computing can be sold as a utility, like water and electricity."
1999
Salesforce.com implements the utility-computing idea commercially.
2002
Amazon launches AWS — storage and compute over the internet.
2006
Amazon launches EC2 (Elastic Compute Cloud), open to everybody.
2009
Google Cloud & Microsoft Azure launch; IBM, Oracle, Alibaba, HP soon follow.

Broader eras of the evolution

Early 2000sModern Cloud PlatformsAWS introduced scalable cloud services, followed by Azure and Google Cloud.

02 · The formal definition

Basics of Cloud Computing — the NIST Definition

NIST definition: Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (networks, servers, storage, applications, services) that can be rapidly provisioned and released with minimal management effort or service-provider interaction.

This one definition packs in the entire unit — it's composed of:

03 · The 5 essential characteristics

Key Features of Cloud Computing

⚡On-Demand Self-Service

Users provision resources (servers, storage) themselves — no human interaction with the provider needed.

Example: AWS EC2 — launch a VM from the console in minutes.
Use case: a startup deploys a test server instantly, no waiting on IT.

🌐Broad Network Access

Services are reachable over the internet from any device — laptop, phone, tablet.

Example: Google Workspace — Docs/Gmail from anywhere.
Use case: a team co-edits a doc live across devices and locations.

🧩Resource Pooling

Resources are shared among many users (multi-tenant), dynamically allocated by demand.

Example: Azure hosts many orgs on shared physical infra with logical isolation.
Use case: one server hosts a small business site and another tenant's analytics workload.

📈Rapid Elasticity / Scalability

Resources scale automatically up or down to match workload.

Example: Netflix on AWS Auto Scaling during a big release.
Use case: an e-commerce site scales up for a sale, back down after.

💳Measured Service

Pay only for what you actually consume — usage is metered and transparent.

Example: Google BigQuery bills by data processed, not a flat fee.
Use case: a research team pays only for the compute a training run actually used.

05 · How it's structured

Cloud Architecture — Layers

From the user's screen down to the physical building — four layers, each abstracting the one below it:

Application Layer SaaS · where end-users interact — email, docs, CRM, streaming (Gmail, Netflix, Salesforce)
Platform Layer PaaS · dev/runtime environment — frameworks, APIs, CI/CD (App Engine, Elastic Beanstalk, Heroku)
Infrastructure Layer IaaS · virtualized compute/storage/network (EC2, Azure VMs, Compute Engine)
Datacenter Layer Physical hardware — servers, power, cooling, physical security
↑ Closer to the user, more abstracted ↓ Closer to physical hardware

Application Layer — key features

  • End-user interface to access cloud apps/services
  • On-demand delivery, usually pay-as-you-go
  • Scales dynamically; supports multi-tenancy
  • High availability via distributed architectures

Platform Layer — key features

  • Pre-configured dev environments — frameworks, APIs, tools
  • Abstracts away servers/networking/storage entirely
  • Integrated databases, analytics, middleware, CI/CD
  • Supports multiple languages (Java, Python, Node.js, Ruby, …)
  • Covers the full app lifecycle: code → test → deploy → scale

Infrastructure Layer — key features

  • Virtualization — many VMs on one physical machine
  • Elastic, on-demand provisioning; pay-as-you-go billing
  • High availability via redundancy/failover across data centers
  • Multi-tenant security & isolation

Datacenter Layer — key features

  • Physical servers, storage, networking hardware
  • Redundant power/cooling/networking for high availability
  • Scales horizontally (add servers) or vertically (upgrade hardware)
  • Physical security — biometrics, surveillance, secured perimeters

Scale (2024-ish figures from the deck): AWS ~125 physical data centers worldwide · Azure ~300 data centers across 60+ regions · Google Cloud 37 data centers in 13 countries · IBM Cloud 60 data centers across 19 countries.

SaaS — Software as a Service

Fully functional software delivered over the internet — access via browser, no install, provider handles maintenance/updates.

✅ Advantages

  • No hardware/setup costs
  • Automated upgrades
  • Cross-device, pay-as-you-go
  • Easy customization & scalability

⚠️ Disadvantages

  • Loss of control
  • Limited range of solutions
  • Must have connectivity
Examples: Google Workspace, Salesforce CRM, Microsoft 365. Use case: an enterprise runs Salesforce for CRM without hosting anything on-prem.

PaaS — Platform as a Service

A development & runtime environment — build, test, deploy, manage apps without touching servers.

✅ Advantages

  • Highly scalable, multi-tenant by default
  • Faster, simpler dev process
  • Less coding, automated policy
  • Easy hybrid-cloud migration

⚠️ Disadvantages

  • Data security concerns
  • Not everything is cloud-enabled
  • Dependent on vendor reliability
Examples: Google App Engine, Azure App Services, AWS Elastic Beanstalk, Heroku, Red Hat OpenShift. Use case: a dev team ships an app fast without managing infrastructure.

IaaS — Infrastructure as a Service

Virtualized compute, storage, and networking — the foundational building blocks, rented instead of owned.

✅ Advantages

  • Most flexible & dynamic model
  • Cost-effective, pay-as-you-go
  • Automated hardware deployment
  • Frees staff from physical infra work

⚠️ Disadvantages

  • Multi-tenant security concerns
  • Vendor outages block data access
  • Team needs training on new infra
Examples: AWS EC2/EBS/VPC, Azure VMs, GCP Compute Engine, IBM Cloud Bare Metal. Use case: a startup hosts its site on virtual servers with zero physical hardware investment.

07 · Where the cloud lives

Four Deployment Models

NIST classifies deployment into four types — this is about who the cloud is for, not what's being delivered.

🌍Public Cloud

Provisioned for open use by the general public; exists on the provider's premises.

Providers: AWS, Azure, GCP, IBM, Oracle.
Examples: Netflix (streaming at scale), Coursera (global course delivery), Airbnb (rapid global scaling).

🔒Private Cloud

Exclusive use by a single organization — owned/managed by the org, a third party, or both; on- or off-premises.

Vendors: Cisco, Dell EMC, Oracle, VMware, HPE.
Examples: CIA (AWS GovCloud, sensitive intel data), JPMorgan Chase (core banking, PCI DSS compliance).

🔀Hybrid Cloud

Two or more distinct clouds (private/community/public) bound together — enables data/app portability, e.g. cloud bursting.

Tech: AWS Outposts, Azure Arc, Google Anthos, VMware Cloud on AWS.
Examples: Goldman Sachs (sensitive data on-prem + AWS for CRM/risk modeling), AT&T (private core network + IBM Cloud for AI support).

🤝Community Cloud

Exclusive use by a specific community with shared concerns (mission, security, compliance) — owned by one, several, or a third party.

Vendors: Cloud4C, HPE, IBM, Microsoft, Cisco.
Examples: Healthcare Information Exchange (HIPAA-compliant patient data sharing), university research-collaboration clouds.

08 · Front-end / back-end split

Cloud Architecture Components

Every cloud architecture has 4 core pieces: a frontend platform, a backend platform, a cloud-based delivery model, and a network connecting them.

🖥️ Frontend

  • Client infrastructure — UI, client-side apps
  • The device/browser the user interacts with
  • e.g. opening a browser, editing a Google Doc
⇄Internet
(the medium connecting them)

🗄️ Backend

  • Application — fulfills client requests
  • Service — manages access to storage/dev-envs/web-apps
  • Runtime cloud — the OS-like layer running services via hypervisors
  • Storage — HDD/SSD/persistent disks
  • Infrastructure — CPU, GPU, network hardware
  • Management — middleware coordinating front/back + resources
  • Security — firewalls, backups, debugging, redundancy

10 · What can go wrong

Challenges & Risks in Cloud Adoption

🔓 Security & Privacy

  • Data breaches / unauthorized access
  • Regulatory compliance (GDPR, HIPAA)
  • Shared responsibility — you still secure your own apps/data

🔗 Vendor Lock-In

  • Hard to migrate data/apps between providers
  • Proprietary tools increase dependency

💸 Cost Management

  • Unpredictable pay-as-you-go costs
  • Overprovisioning wastes money
  • Hidden costs (data transfer, training)

🐢 Performance

  • Latency from distant data centers
  • Downtime from outages/maintenance
  • Multi-tenancy can degrade performance

🧩 Integration Complexity

  • Legacy-system integration is hard
  • Hybrid environments need extra tooling/expertise

🎓 Lack of Expertise

  • Skill gaps in-house
  • Training is time-consuming & costly

Mitigating these challenges

  • Conduct a thorough risk assessment before migrating
  • Invest in employee training / hire skilled cloud experts
  • Use provider cost-management tools to monitor usage
  • Implement robust security (encryption, MFA)
  • Work with providers on compliance & data sovereignty
  • Adopt a multi-cloud/hybrid strategy to avoid lock-in
