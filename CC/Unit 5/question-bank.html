Q61Define HPC. Explain the node roles and the three main components of an HPC cluster.5 marks

HPC is the practice of aggregating computing resources to gain performance greater than a single workstation or server, as a custom supercomputer or a cluster of computers (each one a node), on-premises, in the cloud or hybrid.

  • Components: (1) compute nodes running algorithms in parallel; (2) network with low latency and high bandwidth; (3) storage with fast disks and high-speed memory.
  • Used in research, simulation, design, business intelligence (fraud checks on millions of transactions, crash testing, weather forecasts).

Q64Discuss the benefits and considerations of running HPC on the cloud.6 marks

  • Speed: weeks/months on a regular system become hours.
  • Flexibility and efficiency: scale up/down on demand, pay only for what is used.
  • Cost savings: no large upfront equipment cost, less maintenance; fault tolerance: one node failing does not crash the system.
  • Accelerated R&D (pharma modelling, simulation instead of physical testing) and security (VPC networks, firewalls, confidential computing).

Considerations: latency and bandwidth (robust, low-latency networking); performance (choose providers that keep hardware current); sustainability (high electricity use; prefer renewable-energy clouds); scalable storage (managed services such as Filestore, Managed Lustre).

Google Cloud mapping: Compute Engine (VMs), Cloud Storage (datasets), Networking (low latency), Batch (job scheduling), GKE (containerised workloads).

Q65Numerical: a film studio must render 1000 frames, each taking 6 minutes on one node. Find the ideal time on a single node and on 50 identical cloud nodes, and the speedup.4 marks

Rendering is a loosely coupled workload: frames are independent, so no inter-node communication is needed.

  • Single node: 1000 × 6 = 6000 min = 100 h.
  • 50 nodes: 1000 / 50 = 20 frames per node, so 20 × 6 = 120 min = 2 h.
  • Speedup = 100 / 2 = 50× (ideal; real jobs lose a little to scheduling and storage I/O).

A tightly coupled job (weather simulation) would fall short of this ideal because of MPI communication between nodes. (Worked illustration, not in the deck.)

WRR: weights 2, 1, 1 (a 4-core server = 2, 2-core = 1) give shares 2/4, 1/4, 1/4 = 50%, 25%, 25%, i.e. 500, 250, 250 of 1000 requests.

Least connections: active connections 10, 6, 4 with weights 2, 1, 1 give 10/2 = 5, 6/1 = 6, 4/1 = 4; the minimum is 4, so the next request goes to server 3.

Q69Why use consistent hashing instead of hash(key) mod N? Compute the keys remapped when a 4-server pool grows to 5 (1000 keys).5 marks

  • mod N: adding one server changes N, so most keys remap, destroying cache/session locality.
  • Consistent hashing: servers and keys are hashed onto a ring; each key goes to the next server clockwise. Adding/removing a node moves only about 1/N of keys; virtual nodes even out uneven arcs; Maglev-style tables trade a little balance for fast stable mapping.

Numerical (1000 keys, 4 → 5 servers): with mod, a key stays only if k mod 4 = k mod 5, true for 4 of every 20 consecutive keys (20%), so about 80% = 800 keys move. With consistent hashing about 1/5 = 20% = 200 move. (Worked illustration, not in the deck.)

Q70Explain health checks and failure detection. Numerical: probe interval 10 s, timeout 5 s, unhealthy threshold 3, healthy threshold 2. Find worst-case detection time.4 marks

Active probes: TCP connect or HTTP GET /healthz expecting 200. Passive checks: eject nodes after consecutive 5xx/timeouts (outlier detection). Connection draining lets in-flight requests finish before removal. Keep health endpoints cheap; deep dependency checks can cause cascading ejections.

Worst-case detection ≈ interval × unhealthy threshold = 10 s × 3 = 30 s. By the same logic, a recovered node needs 2 consecutive successes, about 2 × 10 = 20 s to be marked healthy again.

Q72Define the imbalance factor and Jain's fairness index. Interpret the deck's results and compute them for a 4-server example.6 marks

  • Imbalance factor = max(load) / mean(load); 1.0 means perfectly even.
  • Jain's index J = (Σx)² / (n · Σx²); ranges from 1/n (worst) to 1 (even).

Q73Explain the queueing view of headroom, W = (1/μ)/(1−ρ). Numerical: service rate μ = 100 requests/s; find W at ρ = 0.5, 0.9, 0.95, and L at λ = 80/s.5 marks

μ = service rate, ρ = utilization, 1/μ = service time, W = time in system. Delay grows without bound as ρ → 1, so plan capacity for peaks, not averages. Little's Law: L = λ · W.

Service time 1/μ = 1/100 s = 10 ms.

Scale out when load crosses an upper threshold, scale in when it stays low. Cooldown waits after an action; stabilization uses recent recommendations to damp flapping (especially scale-in); warm-up excludes new instances from metrics until ready.

Target tracking: desired = ceil(current × metric / target).

  • Scale out: ceil(4 × 80/50) = ceil(4 × 1.6) = ceil(6.4) = 7 instances.
  • Scale in (own example): ceil(7 × 20/50) = ceil(2.8) = 3 instances.

Q75Explain VM placement as bin packing and describe pre-copy live migration.6 marks

VM placement: pack VMs onto the fewest hosts under CPU, RAM and network limits. It is NP-hard, so use heuristics (First Fit, Best Fit, First Fit Decreasing) or metaheuristics (genetic algorithm, PSO, ant colony). Trade-off: consolidation saves energy but raises contention risk.

Monitoring and alarms (CPU, requests, latency) drive auto-scaling.

  1. Define scope and pick one provider (AWS / Azure / GCP free tier).
  2. Network: VPC with public and private subnets, only 80/443 public.
  3. Package a stateless app image (VM or Docker), sessions in a shared store.
  4. Managed database in a private subnet, object storage, backups.
  5. Launch at least 2 instances across zones from a launch template.

  7. Auto-scaling: min/max, target tracking (CPU 50%), cooldown.

  9. Test: load test, kill an instance to show failover, watch scale-out/in.

Report: problem statement, architecture diagram and service-model mapping, configuration screenshots, test results and cost estimate, challenges and future scope. Demo: open via the LB URL, show load spreading, trigger scaling, stop an instance and show the app stays up.
