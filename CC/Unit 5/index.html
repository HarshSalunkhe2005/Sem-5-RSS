01 · Aggregating computers to act as one supercomputer EXAM SCOPE FROM DECK

High Performance Computing (HPC) — Fundamentals

HPC is the practice of aggregating computing resources to gain performance greater than that of a single workstation, server, or computer. It can take the form of custom-built supercomputers or groups of individual computers called clusters, and can run on-premises, in the cloud, or hybrid. Each computer in a cluster is a node, each responsible for a different task.

Node roles in a cluster

🎛️Controller nodes

Run essential services and coordinate work between nodes.

🔑Interactive / login nodes

Hosts users log in to, via GUI or command line.

🧮Compute nodes

Execute the computations; algorithms and software run in parallel on each node.

Three main components

1. Compute

Nodes connected to other nodes to run algorithms and software simultaneously.

2. Network

Connects nodes to each other and to data servers; nodes exchange results, so it needs low latency, high bandwidth.

3. Storage

Data servers capture the output; needs fast disks and high-speed memory.

HPC lets companies and researchers solve problems that are too large for standard computers or would take too long — hence also called supercomputing. Used in academic research, science, design, simulation and business intelligence. Examples: banks verifying fraud on millions of credit-card transactions at once, automakers crash-testing a car design, tomorrow's weather forecast.

Why important: the ecosystem is flooded with data and compute-intensive tools; HPC processes it in time, enabling forecasting of business scenarios, market prediction and recommendations. In medicine it helps model outbreaks, decode the genome of cancerous cells and understand how diseases evolve — accelerating scientific, technological and business progress.

HPC Design Types & Workloads (+ MPI)

Two general design types

TypeDescription
Cluster computingParallel computing by a collection of computers working together — servers placed close to each other physically and in network topology to minimize latency between nodes.
Distributed computingConnects computing power of multiple computers in a network that is in a single location (often on-premises) or spread across several locations, possibly mixing on-premises hardware and cloud resources.

Homogeneous vs heterogeneous clusters

HomogeneousHeterogeneous
All machines have similar performance and configuration; treated as the same and interchangeable. Hardware with different characteristics (high CPU core-count, GPU-accelerated, etc.); best utilized when nodes are assigned tasks that leverage their distinct advantages.

How HPC jobs work — two workload types

Loosely coupledTightly coupled
Also calledParallel / high-throughput jobs—
NatureIndependent tasks run at the same time across the system; may share common storage but are not context-dependent, no need to communicate results.Many small processes, each on a different node, dependent on each other to complete the overall task.
NeedsLittle inter-node communication.Low-latency networking between nodes; fast access to shared memory and storage.
CommunicationNone needed between tasks.Interprocess communication via MPI (Message Passing Interface) — software such as OpenMPI and Intel MPI.

03 · Renting a supercomputer by the hour EXAM SCOPE · high-yield FROM DECK

HPC on Cloud — Benefits, Considerations, Use Cases

HPC can run on-premises with dedicated equipment, in the cloud, or hybrid. HPC in the cloud gives flexibility and scalability without buying and maintaining expensive supercomputers. It provides the needed infrastructure — data storage, networking, specialized compute, security and AI applications. Workloads run on demand: pay only for resources used, when needed.

Considerations when running HPC in the cloud

Latency & bandwidth

Robust networking (>100 GB/s as stated in the deck) with low latency.

Performance

Best with providers that constantly update systems — processors, storage, networking.

Sustainability

Needs far more electricity; on-prem can cost millions a year in energy. Clouds prioritizing renewable energy (e.g. Google Cloud) mitigate this.

Storage

Scalable storage matters; managed services such as Filestore or Managed Lustre are an advantage.

Benefits

⚡ Speed & performance

Weeks/months on a regular system become hours.

🔄 Flexibility & efficiency

Scale up/down on need; access from anywhere with a robust connection.

💰 Cost savings

Saves time and money on compute resources and labour hours.

🛡️ Fault tolerance

If one node fails the rest of the system does not crash.

🔬 Accelerated R&D

Faster results for pharma modelling, designing machines/parts, simulating experiments to cut physical testing.

🔒 Security

Privately managed global infrastructure; VPC networks connect nodes and configure firewalls; Confidential Computing gives encryption in use, at rest and in flight.

💸 Initial cost

On-prem clusters/supercomputers have high upfront cost (equipment, labour, software, configuration) — out of reach for most.

🌱 Energy

On-prem energy costs are large; cloud HPC can be sustainable on the cleanest cloud.

🛠️ Maintenance

HPC needs latest hardware and optimized software; keeping on-prem current is a large ongoing expense.

Use cases

Load Balancing — Why, How, Layer 4 vs Layer 7

Why load balancing matters

1 · Performance

Spreads requests so no server becomes a bottleneck.

2 · Availability

Reroutes traffic away from failed or unhealthy nodes.

3 · Scalability

Adds or removes capacity as demand changes.

4 · Cost efficiency

Higher utilization means fewer idle resources to pay for.

Load-Balancing Algorithms & Consistent Hashing

TypeAlgorithmBest suited for
StaticRound RobinUniform servers, similar requests
StaticWeighted Round RobinServers with unequal capacity
DynamicLeast ConnectionsLong-lived, uneven sessions
DynamicLeast Response TimeLatency-sensitive services
Hash-basedIP HashSession affinity without state sharing
AdaptivePredictive / ML-basedBursty, forecastable workloads

Algorithm mechanics

Weighted Round Robin

share_i = w_i / Σw

Weights reflect capacity, e.g. 4-core = 2, 2-core = 1.

Least Connections

argmin(active_i / w_i)

Tracks open connections; weight-normalized for mixed hardware.

Power of Two Choices

sample 2, pick lighter

Avoids scanning every server; max load falls sharply vs pure random.

Peak EWMA Latency

ewma_rtt × (inflight+1)

Favors fast, lightly loaded backends and adapts to slow nodes.

Consistent hashing

Diagram · Hash ring

S1
→
S2
→
S3
→
S4
↩ (ring)
key → hashed onto ring → next server clockwise
  • Plain hash(key) mod N: adding one server remaps most keys.
  • On the ring, each key goes to the next server clockwise.
  • Adding or removing a node moves only about 1/N of keys.
  • Virtual nodes even out uneven arcs.
  • Maglev-style lookup tables trade a little balance for fast, stable mapping.

Forwarding Modes, Health Checks & Session Persistence

Forwarding modes and balancer topologies

ModeHow it worksTrade-off
Proxy (full NAT)LB terminates the client connection and opens a new one to the backendFull L7 control; all traffic in both directions crosses the LB
Direct Server ReturnLB rewrites the destination MAC; backend replies straight to the clientHigh throughput; no L7 features, VIP on loopback
IP tunnelingLB encapsulates packets (IP-in-IP/GRE) to backendsWorks across subnets; adds MTU overhead
ECMP + anycastRouters spread flows over LB instances by 5-tuple hashScales LBs horizontally; flows can remap when instances change
DNS / GSLBName resolves to different regional addressesGlobal steering; failover limited by TTL

Health checks and failure detection

ParameterExample
Probe interval10 s
Probe timeout5 s
Unhealthy threshold3 failures
Healthy threshold2 successes

Worst-case detection ≈ interval × unhealthy threshold ≈ 10 s × 3 = 30 s.

  • Active probes: TCP connect or HTTP GET /healthz expecting 200.
  • Passive checks: eject nodes after consecutive 5xx or timeouts (outlier detection).
  • Connection draining: let in-flight requests finish before removal.
  • Keep health endpoints cheap; deep dependency checks can cause cascading ejections.

Session persistence and state

MethodMechanismDrawback
Source-IP affinityHash of client IP picks the backendClients behind one NAT pile onto one server
LB-inserted cookieLB sets a cookie naming the backend (L7)Session lost if that backend is removed
App session IDLB routes on an application cookieLB must understand the app protocol
Stateless + shared storeSessions kept in Redis or a database; any node servesExtra latency; the store becomes a dependency

Prefer stateless services: balancing, scaling and failover all become simpler.

07 · Measuring how well capacity is used EXAM SCOPE · numericals FROM DECK

Resource Utilization — Metrics, Imbalance & Queueing

What to measure

CPU

Processing load per VM or container.

Memory

Working set vs allocated RAM.

Network I/O

Bandwidth and packets per second.

Response time

Latency and request queue depth.

Goal: keep average utilization high enough to avoid waste, with headroom to absorb spikes and meet SLAs.

Impact of load balancing

Without balancing

Hot spots and idle nodes coexist, wasting capacity.

With balancing

Load evens out, so the same fleet handles more traffic.

The deck's chart uses illustrative CPU data.

Quantifying load imbalance

Imbalance factor

max(load) / mean(load)

1.0 means perfectly even.

Jain's fairness index

J = (Σx)² / (n·Σx²)

Ranges from 1/n (worst) to 1 (even).

MetricBefore balancingAfter balancing
Max / mean1.711.05
Jain's index0.791.00

Computed from the illustrative CPU values on the deck's utilization chart. Reading: max/mean fell from 1.71 to 1.05 (closer to 1.0), Jain's rose from 0.79 to 1.00, and spread shrank from 28.1 to 2.2 pp.

Why headroom matters — a queueing view

W = (1/μ) / (1 − ρ)   Little's Law: L = λ·W

Delay grows without bound as ρ (utilization) approaches 1, so plan capacity for peaks, not averages. (Worked illustration, not in the deck: at ρ = 0.5, W = 2 × service time; at ρ = 0.9, 10×; at ρ = 0.95, 20×.)

08 · Matching capacity to demand automatically EXAM SCOPE · numericals FROM DECK

Auto-Scaling, VM Placement & Live Migration

The auto-scaling feedback loop

Diagram · Auto-scaling feedback loop

1 · Monitor metrics
→
2 · Evaluate policy
→
3 · Scale out / in
→
4 · Rebalance traffic
↩ repeat

Scale out when load crosses an upper threshold; scale in when it stays low, using cooldown periods to avoid flapping.

Target-tracking math

desired = ceil( current × metric / target )

Worked example: 4 instances at 80% CPU, target 50% → ceil(4 × 80/50) = ceil(4 × 1.6) = ceil(6.4) = 7 instances.

Cooldown

Wait after a scaling action before acting again.

Stabilization

Use recent recommendations to damp flapping, especially on scale-in.

Warm-up

Exclude new instances from metrics until they are ready.

VM placement as bin packing

  • NP-hard: pack VMs onto the fewest hosts under CPU, RAM and network limits.
  • Heuristics: First Fit, Best Fit, First Fit Decreasing.
  • Metaheuristics: genetic algorithm, PSO, ant colony.
  • Trade-off: consolidation saves energy but raises contention risk.

Live migration (pre-copy)

Diagram · Pre-copy live-migration rounds

Round 1copy memory pages while VM runs
→
Round 2…nre-copy pages dirtied meanwhile
→
Brief pauselast dirty pages + CPU state
→
ResumeVM runs on destination host
  1. Copy memory pages while the VM keeps running.
  2. Re-copy pages dirtied meanwhile, in rounds.
  3. Pause briefly; send last dirty pages and CPU state.
  4. Resume on the destination host.

Cost: network and CPU; high dirty-page rates prolong migration.

09 · Problems, fixes, provider services and good habits EXAM SCOPE FROM DECK

Challenges, Techniques, Cloud LB Services & Best Practices

Challenges

  • Unpredictable, bursty traffic
  • Heterogeneous VMs and hardware
  • Balancer as a single point of failure
  • Migration overhead and SLA limits

Optimization techniques

  • Auto-scaling with health checks
  • VM migration and consolidation
  • Multi-tier and global balancing
  • Energy-aware and ML-driven scheduling

Load balancing in major clouds

CloudServiceNotes
AWSElastic Load BalancingApplication, Network and Gateway load balancers
Microsoft AzureLoad Balancer, Application GatewayLayer 4 balancing plus Layer 7 gateway; Front Door for global routing
Google CloudCloud Load BalancingGlobal and regional balancing behind a single anycast IP

Service names as commonly offered; check provider documentation for current options.

Best practices

  1. Run balancers redundantly across zones.
  2. Configure health checks and graceful draining.
  3. Design services to be stateless where possible.
  4. Terminate SSL at the balancer and monitor continuously.
  5. Load test and tune scaling thresholds regularly.

Key takeaways

  • Load balancing keeps cloud services responsive and available.
  • The right algorithm depends on workload and server heterogeneity.
  • Better utilization cuts cost and energy use.
  • Future direction: adaptive, ML-based and energy-aware balancing.

Mini Project — Scalable Web App on the Cloud

Note: the lecture decks contain nothing on the mini project. This section is a practical guide written from standard cloud knowledge; adapt it to whatever your faculty specifies.

Suggested project: deploy a simple web application (e.g. a notes or complaint portal) that is highly available and scales automatically — tying together virtual machines/containers, a load balancer, auto-scaling, storage and monitoring.

Step-by-step checklist

  1. Define scope: app, expected users, availability and cost goals; pick one provider (AWS / Azure / GCP free tier).
  2. Network: create a VPC/virtual network with public and private subnets; configure security groups/firewall (only 80/443 public).
  3. Build the app image: package the app (VM image or Docker container) with a stateless design; keep sessions in a shared store.
  4. Data layer: managed database in a private subnet; object storage for files/static assets; enable backups.
  5. Compute: launch at least 2 instances across zones from a launch template.
  6. Load balancer: create it, add a target group, configure a /healthz health check and connection draining.
  7. Auto-scaling: set min/max, a target-tracking policy (e.g. CPU 50%) and cooldown.
  8. Monitoring: dashboards and alarms for CPU, memory, request count and latency; set a billing alert.
  9. Test: load-test the app, kill an instance to show failover, and watch scale-out/scale-in.
  10. Clean up: delete resources to avoid charges.

What to document and present

Report

  • Problem statement and objectives
  • Architecture diagram and service-model mapping (IaaS/PaaS)
  • Configuration details and screenshots
  • Test results (scaling, failover) and cost estimate
  • Challenges, limitations, future scope

Demo

  • Open the app via the load-balancer URL
  • Show load being spread across instances
  • Trigger load and show auto-scaling
  • Stop an instance and show the app stays up
  • Show the monitoring dashboard

Likely exam questions

Q1. Define HPC and explain node types.

HPC aggregates computing resources (clusters/supercomputers) for performance beyond a single machine. Controller nodes coordinate work, login nodes are user entry points, compute nodes run the parallel computations.

Q2. Loosely vs tightly coupled workloads?

Loosely coupled: independent tasks, no communication (CGI rendering). Tightly coupled: interdependent processes needing low-latency networking and MPI (weather forecasting).

Q3. Benefits and considerations of HPC on cloud?

Benefits: speed, flexibility, cost savings, fault tolerance, faster R&D, security, no upfront or maintenance cost. Considerations: latency/bandwidth, performance, sustainability, scalable storage.

Q4. Compare Layer 4 and Layer 7 load balancing.

L4 routes on IP/port, fast, protocol-agnostic, blind to content. L7 routes on HTTP path/host/headers, supports SSL termination, caching and cookie affinity at higher CPU cost.

Q5. Explain any three LB algorithms.

Round robin: cyclic, for uniform servers. Weighted RR: share = w_i/Σw for unequal capacity. Least connections: argmin(active_i/w_i) for uneven long sessions. (Also IP hash, power of two choices.)

Q6. Why consistent hashing over hash mod N?

With mod N, adding a server remaps most keys. With a ring, only about 1/N of keys move; virtual nodes balance arcs.

Q7. 4 instances at 80% CPU, target 50%: how many?

desired = ceil(4 × 80/50) = ceil(6.4) = 7 instances; cooldown and stabilization prevent flapping.

Q8. Describe pre-copy live migration.

Copy memory pages while the VM runs, re-copy dirtied pages in rounds, pause briefly to send final dirty pages and CPU state, then resume on the destination. High dirty-page rates prolong it.
