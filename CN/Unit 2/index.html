01 · How apps are structured

Network Application Architectures

Client-Server

One component (client) requests services from another (server). Classic web apps: browser = client, web server = server.

Peer-to-Peer (P2P)

Every component is both client and server, communicating directly with any other — the model behind file-sharing apps.

Three-Tier

Client → middleware → database, adding a layer of abstraction that improves performance and scalability.

Microservices

The app is a collection of small, independently deployable services communicating via APIs — the opposite of a tightly-coupled monolith.

Why companies move to microservices

Amazon, Netflix, and Uber all migrated away from monolithic architectures as they scaled — each service can be built, deployed, and updated independently without risking the whole application, and a failing service can be routed around rather than taking everything down.

Worked example — Amazon checkout, one microservice per step

  1. Customer clicks Buy Now → request hits the API Gateway.
  2. API Gateway forwards to the Order Service.
  3. Order Service checks the Inventory Service.
  4. Order Service contacts the Payment Service.
  5. After payment succeeds, Order Service messages a Messaging Broker.
  6. The broker fans out to Email, SMS, and Shipping services simultaneously.

02 · From application to wire

Processes Communicating & the Socket Interface

Two processes (possibly on different machines) communicate via protocols that define the rules and data formats. The interface between a process and the network is the network stack — a collection of protocols/services that translates the process's requests into actual network protocol messages, and back.

Real-life analogy: You (process) hand a package to the courier office (socket/API interface). The courier company (network stack) handles packaging, routing, and delivery over the road network (Internet) to another person (receiving process). You never touch the actual delivery mechanics.

Transport services available to applications

ServiceReliable?Best for
TCPYes — connection-oriented, error-checked, flow-controlledEmail, file transfer — anything needing accuracy
UDPNo — connectionless, no error/flow controlVideo streaming, gaming — anything needing speed/low latency
SCTPYes — reliable, multi-homed, multi-streamApplications needing several parallel data streams
DCCPNo, but congestion-controlledApps wanting congestion control without full reliability

Sockets

A socket = IP address + port number — it's how the network stack knows exactly which application on which machine data belongs to. 192.168.1.67:80 is a socket. TCP sockets (stream) give reliable, connection-based communication; UDP sockets (datagram) give faster, connectionless, unreliable communication.

03 · The protocol of the Web

HTTP — Evolution & How It Works

HTTP was released in 1991 by Tim Berners-Lee, with the launch of the World Wide Web.

VersionYearMajor featuresLimitation solved
HTTP/0.91991Only GET methodBasic web communication
HTTP/1.01996POST/PUT/DELETE, headers, status codes, MIME typesRicher client-server communication
HTTP/1.11997Persistent connections, pipelining, cachingReduced connection overhead
HTTP/22015Multiplexing, header compression (HPACK), server pushFaster page loads, better bandwidth use
HTTP/32020Runs over QUIC (over UDP) instead of TCPBetter performance on unreliable networks, no head-of-line blocking

Basic features of HTTP

Stateless

Each request is independent — client/server "forget" each other unless cookies/sessions are used.

Connectionless

The connection closes after each request completes (in the basic model).

Media independent

Any data type can be sent, as long as MIME type is specified.

HTTP message anatomy

Every HTTP message has three parts: a start line (Request-Line or Status-Line), headers (General/Request/Response/Entity), and a message body (the actual data — HTML, JSON, files, etc.).

Request:  GET /hello.htm HTTP/1.1
Response: HTTP/1.1 200 OK

Step-by-step: loading a webpage

  1. User enters a URL (e.g. https://www.facebook.com) and presses Enter.
  2. Browser sends an HTTP GET request to the server.
  3. Server processes the request, prepares an HTML response.
  4. Browser receives the HTML — which references images, CSS, JS, videos.
  5. Browser fires a separate GET request for every referenced resource.
  6. Once everything arrives, the browser assembles and displays the complete page.

Caching & proxy servers

Web caching saves a copy of a response the first time it's fetched, so later requests are served instantly without hitting the origin server again. A proxy server sits between client and origin: checks if it has a local copy first, serves it directly if so — otherwise fetches on the client's behalf and caches the result. Benefits: faster repeated requests, lower bandwidth cost, less overall Internet traffic.

04 · Moving files and mail

FTP & SMTP

File Transfer Protocol (FTP)

FTP transfers files between client and server, shielding the user from differences in OS/directory structure/character sets across systems. It uses two connections: a control connection (port 21, for commands/login) and a data connection (port 20, for the actual file).

Variants

Anonymous FTP (no login needed, limited access), Password-Protected FTP, FTPS (FTP over SSL/TLS), FTPES (explicit TLS upgrade), SFTP (actually a subset of SSH, port 22 — not really "FTP" at all).

Trade-offs

Pros: simple, efficient, resumable, fast. Cons: plaintext credentials by default (insecure), old protocol, firewall-unfriendly (multiple TCP connections).

Simple Mail Transfer Protocol (SMTP)

SMTP is used between mail servers to exchange email. The client opens a TCP connection to the server (traditionally on port 25; modern secure submission uses port 587 with TLS).

Flow: Sender → User Agent (Gmail/Outlook) → Mail Queue → Client MTA → SMTP/TCP → Server MTA → User Mailbox → User Agent → Receiver.

Delivery models: End-to-end (between organizations — client waits until the email is copied to the recipient's server) vs. Store-and-forward (within an organization — email may hop through several intermediate MTAs, sender is notified once it reaches just the first hop).

05 · The Internet's address book

Domain Name System (DNS)

DNS translates human-readable names (www.google.com) into machine-readable IP addresses (142.250.190.14) — a hierarchical, distributed database.

How a lookup works

  1. Check local cache (browser/OS/router) — if found, done.
  2. Otherwise, query goes to a DNS resolver.
  3. Resolver asks a Root server, which points to the right TLD server (e.g. .edu).
  4. TLD server points to the Authoritative server for that exact domain.
  5. Authoritative server returns the actual IP address, which flows back to your browser.

Query types

Recursive: server must return a final answer or error. Iterative: server gives the best answer it has. Non-recursive: answer comes straight from cache.

Caching & TTL

Records are cached locally to avoid repeat lookups. TTL (time-to-live) is how long a record stays cached before a fresh lookup is required.

Domain types

Generic: .com, .edu, .org, .net. Country: .in, .us, .uk. Inverse: IP → domain name mapping (e.g. via nslookup).

06 · No central server

P2P Architectures

Centralized Directory

A central server tracks which peer has which file (Napster-style). Simple, but a single point of failure — if the server crashes, the whole network crashes.

Query Flooding

Fully decentralized (Gnutella-style) — a request is forwarded to all neighboring peers until a match is found. No single point of failure, but highly inefficient/unscalable at large size.

Exploiting Heterogeneity

KaZaA-style hybrid — high-bandwidth peers become "supernodes" that index their child peers, limiting the scope of query flooding while staying decentralized.
