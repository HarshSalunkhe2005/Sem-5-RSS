Network address and Host ID from IP + subnet mask

Rule: a 1 in the mask marks a network bit, a 0 marks a host bit. Network address = IP AND mask. Host ID = the host-bit part of the IP (IP AND NOT mask).

Q1 (deck). 172.16.5.120 with mask 255.255.0.0

IP address: 172.16.5.120  |  Subnet mask: 255.255.0.0 (/16)
  1. Split the mask/16 means the first 16 bits are network, the remaining 16 bits are host
  2. Network address (keep the first two octets, zero the host octets)172.16 . 0 . 0 = 172.16.0.0
  3. Host ID (the last two octets)5.120, in binary 00000101.01111000
Network address = 172.16.0.0; Host ID = 5.120

Q2 (deck). 10.20.30.45 with mask 255.0.0.0

IP address: 10.20.30.45  |  Subnet mask: 255.0.0.0 (/8)
  1. Split the mask/8 means the first 8 bits are network, the remaining 24 bits are host
  2. Network address10 . 0 . 0 . 0 = 10.0.0.0
  3. Host ID (last three octets)20.30.45, in binary 00010100.00011110.00101101
Network address = 10.0.0.0; Host ID = 20.30.45

Three more examples Beyond the deck

Q4. 172.31.200.9 with mask 255.255.240.0 (mask cuts inside an octet)

IP: 172.31.200.9  |  Mask: 255.255.240.0 (/20 = 16 + 4 bits in the third octet)
  1. Binary of the third octetIP: 200 = 11001000; Mask: 240 = 11110000
  2. AND the third octet11001000 AND 11110000 = 11000000 = 192
  3. Network address172.31.192.0 (first two octets unchanged, last octet 0 because the mask byte is 0)
  4. Host bitsthird octet: 11001000 AND 00001111 = 00001000 = 8; fourth octet: 9. Host ID = 0.0.8.9
  5. Check12 host bits: 212 - 2 = 4094 usable hosts; broadcast = 172.31.207.255 (host bits all 1)
Network address = 172.31.192.0; Host ID = 0.0.8.9 (host number 8x256 + 9 = 2057)

Q5. 10.5.130.200 with mask 255.255.255.192

IP: 10.5.130.200  |  Mask: 255.255.255.192 (/26 = 24 + 2 bits in the fourth octet)
  1. Binary of the fourth octetIP: 200 = 11001000; Mask: 192 = 11000000
  2. AND the fourth octet11001000 AND 11000000 = 11000000 = 192
  3. Network address10.5.130.192
  4. Host bits (6 bits)11001000 AND 00111111 = 00001000 = 8. Host ID = 8
  5. Check26 - 2 = 62 usable hosts; subnet range 10.5.130.192 to 10.5.130.255, broadcast 10.5.130.255
Network address = 10.5.130.192; Host ID = 8

Exam shortcut: only the octet where the mask is neither 255 nor 0 needs binary work. Copy octets under 255, zero the octets under 0, and AND just the middle one.

Physical (MAC) vs logical (IP) vs port address

Scenario in the deck: you open a website on your computer. Three different addresses are used at once.

AddressWhat it identifies (deck)LayerSize and example Beyond the deck
Physical (MAC)A network interface on the local network, used for frame deliveryData link48 bits, e.g. 3C:52:82:1A:9F:07; rewritten at every hop
Logical (IP)Source and destination at the network layer, enabling routing between networksNetwork32 bits (IPv4) or 128 bits (IPv6), e.g. 192.168.10.77
PortThe application or service endpoint on a device, such as HTTPS on port 443Transport16 bits (0 to 65535); the client uses a temporary (ephemeral) port

How they work together when you open a website Beyond the deck

  • The browser asks for HTTPS, so the destination port is 443. Your OS picks a temporary source port for the browser.
  • The IP header carries your IP and the web server's IP. These stay the same end to end (ignoring NAT), and routers use the destination IP to forward the packet.
  • The MAC header carries only the next hop: your NIC to the router's NIC. At each router the MAC pair is replaced; the IP pair and ports are not.
  • At the server, the MAC gets the frame to the right interface, the IP to the right host, and the port to the right process (the web server).

Related: Unit 2: how processes communicate and Unit 3: transport layer overview (multiplexing by port).

Socket creation: server-side and client-side steps

TCP uses SOCK_STREAM; UDP uses SOCK_DGRAM. Basic socket Q&A is already in Unit 2 question bank (Q13, Q16).

Server-side process (7 steps)

#CallWhat it does (deck)
1sockfd = socket(domain, type, protocol)Creates the socket and returns a descriptor (an integer, like a file handle). domain: AF_LOCAL for processes on the same host (POSIX), AF_INET for IPv4, AF_INET6 for IPv6. type: SOCK_STREAM = TCP (reliable, connection-oriented), SOCK_DGRAM = UDP (unreliable, connectionless). protocol: 0 for Internet Protocol (the number that appears in the IP header protocol field).
2setsockopt(...)Optional. Sets options on the socket; helps reuse of the address and port.
3bind(sockfd, sockaddr *addr, socklen_t addrlen)Binds the socket to the IP address and port in addr; addrlen is the length of that structure.
4listen(sockfd, backlog)Puts the socket in passive mode, waiting for clients. backlog is the maximum length of the queue of pending connections; if the queue is full a client may get ECONNREFUSED.
5new_socket = accept(sockfd, sockaddr *addr, socklen_t *addrlen)Takes the first pending connection off the queue, creates a new connected socket and returns its descriptor. addr receives the client's IP and port. The connection is now established.
6send(sockfd, *buf, len, flags) / recv(sockfd, *buf, len, flags)Send data to or receive data from the client. buf = data buffer, len = number of bytes, flags = options (0 for default).
7close(fd)Closes the socket and releases the system resources.

Client-side process (4 steps)

#CallWhat it does (deck)
1socket(...)Created exactly as on the server.
2connect(sockfd, sockaddr *addr, socklen_t addrlen)Connects the socket to the server whose IP address and port are in addr.
3send() / recv()Exchange data with the server, same as on the server side.
4close()Closes the socket and releases resources.

Remember: the server has two kinds of sockets. The listening socket (from socket+bind+listen) only accepts connections; accept() returns a fresh socket used to talk to that one client. The client never calls bind, listen or accept (the OS picks its source port).

Call order at a glance Beyond the deck

SERVER: socket -> (setsockopt) -> bind -> listen -> accept -> recv/send -> close
CLIENT: socket ------------------------------> connect -> send/recv -> close
                                   (TCP three-way handshake happens during connect/accept)

Distance Vector Routing and count-to-infinity

The deck's routing slides. This topic is in the PYQs (see the CN PYQs) but has no notes page yet.

Distance Vector Routing (DVR)

A dynamic routing algorithm that routers use to find the best path from a source network to a destination network. Each router keeps a table of Destination, Distance (cost) and Next hop, and shares its table only with its immediate neighbours. Tables are updated until they stop changing (convergence). It is based on the Bellman-Ford equation, dx(y) = min over neighbours v of { c(x,v) + dv(y) }.

  1. Initially each router knows only the cost to itself (0) and to its directly connected neighbours.
  2. Each router sends its distance vector to its neighbours, periodically or when something changes.
  3. A router computes the cost to each destination through each neighbour.
  4. It picks the minimum-cost route and updates its table.
  5. Repeat until no table changes.

Worked example (deck): shortest path from A to C

Link costs from the deck's example: A-B = 1, B-C = 1, A-D = 4, D-C = 1
  1. Via BA-B + B-C = 1 + 1 = 2
  2. Via DA-D + D-C = 4 + 1 = 5
  3. Minimummin(2, 5) = 2, so A reaches C through B

Count-to-infinity problem

Routers keep raising their estimated distance to an unreachable destination because each wrongly believes the other still has a valid path. This causes routing loops and slow convergence.

Deck example: routers A, B, C; network X. Before the failure A = 0 (directly connected), B = 1 (via A), C = 2 (via B). The A-X link then fails. A marks X unreachable (infinity), but B still advertises distance 1 to X; A now thinks it can reach X via B at 1 + 1 = 2; B then hears A's 2 and computes 1 + 2 = 3, and so on.

The values climb until the protocol's defined infinity; the exact sequence depends on update timing. In RIP, 16 hops is infinity, so the count is bounded.

Solutions

  • Split horizon: do not advertise a route back to the neighbour you learned it from.
  • Route poisoning: advertise a failed route with an infinite metric.
  • Poison reverse: advertise a route back to the neighbour you learned it from, but with an infinite metric.
  • Triggered updates: send an update immediately after a significant change, not at the next periodic update.
  • Hold-down timers: after detecting a failure, suppress possibly wrong routing information for a while.

S1 to S4: architectures, HTTP, DNS, email

Background notes: architectures, HTTP, DNS, SMTP. Use Show answer on each question to test yourself.

S1An online shopping company built its whole application as one monolith. Updating the payment module forces a full redeploy, and during festival sales one failing component can take down the whole site. (a) Which architecture would you recommend? (b) How does it improve scalability and fault tolerance? (c) How would the Order, Inventory, Payment, Email/SMS and Shipping services communicate? (d) Give two advantages over a monolith.

(a) Recommendation

Microservice architecture: split the application into small, independently deployable services (Order, Inventory, Payment, Email/SMS, Shipping), each owning one business function and its own data.

(b) Scalability and fault tolerance

  • Scalability: each service scales on its own. In a festival sale you run more copies of Order and Payment behind a load balancer and leave Shipping alone, instead of cloning the whole monolith.
  • Fault tolerance: a failure is contained in one service. If Email/SMS is down the customer can still place and pay for an order, and the notification is sent later. Services can also be restarted or redeployed without stopping the rest.
  • An updated Payment service is redeployed alone, so no full-site redeploy is needed.

(c) Communication Beyond the deck

  • Synchronous request/response (REST over HTTP or gRPC), usually through an API gateway: Order asks Inventory "is the item in stock?" and Payment "charge this amount" because it needs the answer immediately.
  • Asynchronous messaging through a message broker (e.g. RabbitMQ or Kafka): Order publishes an OrderPlaced event; Inventory reserves stock; after Payment publishes PaymentConfirmed, Shipping creates the shipment and Email/SMS sends the confirmation. Queues absorb sale-time spikes and a slow consumer does not block the sender.
  • Sample flow: customer -> API gateway -> Order -> (Inventory check) -> Payment -> event -> Shipping + Email/SMS.

(d) Two advantages over monolithic

  1. Independent deployment and updates: change Payment without redeploying everything.
  2. Fault isolation and independent scaling: one failing component does not bring down the site, and only the busy service needs extra capacity.

Other valid points: each team can pick its own technology, and smaller codebases are easier to understand. Trade-off: more network calls, more operational complexity, harder distributed debugging.

S2A news website has hundreds of images, videos, CSS and JavaScript files. Users complain of slow loading, especially on unstable networks. (a) HTTP/1.1, HTTP/2 or HTTP/3? (b) How does multiplexing improve performance? (c) How does HTTP/3 handle packet loss differently from HTTP/2? (d) Give two advantages of HTTP/3.

(a) Recommendation

HTTP/3 (HTTP/2 as the fallback), because the problem is many objects plus an unreliable network.

(b) Multiplexing

HTTP/1.1 sends one request at a time per connection, so browsers open several TCP connections (commonly about six per host) and a slow object blocks those behind it (head-of-line blocking at the HTTP level). With multiplexing (HTTP/2 and HTTP/3) many requests and responses are interleaved as independent streams over one connection. The page can fetch images, CSS and JS in parallel, a slow video does not block a small CSS file, and only one connection setup (handshake) is paid. Beyond the deck HTTP/2 also adds header compression (HPACK) and binary framing.

(c) Packet loss: HTTP/2 vs HTTP/3 Beyond the deck

  • HTTP/2 runs over TCP. TCP delivers one ordered byte stream, so when one packet is lost, all streams on the connection wait until it is retransmitted. This is TCP-level head-of-line blocking, and it hurts most on lossy links.
  • HTTP/3 runs over QUIC, which runs over UDP. QUIC streams are independent. A lost packet stalls only the stream(s) whose data it carried; the other streams keep delivering. QUIC does its own loss recovery per stream.

(d) Two advantages of HTTP/3 Beyond the deck

  1. No transport-level head-of-line blocking, so better performance on lossy or unstable networks.
  2. Faster connection setup: QUIC combines the transport and TLS 1.3 handshake (1 RTT, or 0-RTT on resumption), and the connection survives a network change (e.g. Wi-Fi to mobile data) because it is identified by a connection ID, not the IP/port pair. Encryption is built in.

S3A student types www.sitpune.edu.in into a browser but the IP address is not in the local cache. (a) Explain the DNS resolution process. (b) Role of the DNS resolver? (c) Roles of Root, TLD and Authoritative servers? (d) How does DNS caching improve performance?

(a) Resolution process

  1. The browser and OS caches have no entry, so the OS sends a query to the configured DNS resolver (recursive resolver, usually the ISP's or a public one).
  2. The resolver checks its own cache; on a miss it queries a root server, which does not know the IP but replies with the address of the TLD server for .in.
  3. The resolver asks the .in TLD server, which replies with the name servers responsible for the next level (edu.in, then the domain's own name servers).
  4. The resolver asks the authoritative name server for sitpune.edu.in, which returns the A record (IP address) for www.sitpune.edu.in.
  5. The resolver caches the answer (for its TTL) and returns it to the client; the browser then opens a TCP connection to that IP.

The course treats the hierarchy as Root, TLD, Authoritative; edu.in is simply one more delegation step on the way (Beyond the deck).

(b) Role of the resolver

It does the work on behalf of the client: the client sends one recursive query ("give me the final IP"), and the resolver performs the series of queries to root, TLD and authoritative servers (iterative queries), caches results, and returns the final answer or an error.

(c) Roles of the servers

  • Root servers: top of the hierarchy; they know where the TLD servers (.com, .edu, .in, ...) are and refer the resolver there.
  • TLD servers: responsible for one top-level domain; they point to the authoritative name servers of domains under it.
  • Authoritative servers: hold the actual records (name to IP) for a domain and give the final, authoritative answer.

(d) Caching

Resolved records are stored (browser, OS, resolver) for the time given by the record's TTL. Repeat lookups are answered from the cache without walking the hierarchy, which cuts lookup time, reduces DNS traffic, and takes load off root/TLD/authoritative servers. Trade-off: a changed record may stay stale until the TTL expires. More in Unit 2 DNS.

S4A faculty member emails an assignment to 100 students. After clicking Send, the mail is queued and passed through mail servers before it reaches the students' mailboxes. (a) Roles of UA, MTA and MDA. (b) Role of SMTP. (c) End-to-end vs store-and-forward delivery. (d) Which transport protocol does SMTP use?

(a) UA, MTA, MDA

  • UA (User Agent): the mail client (Outlook, Gmail app) used to compose, send, read and manage mail.
  • MTA (Mail Transfer Agent): the mail server software that accepts the message from the UA, queues it, and relays it towards the destination mail server (SMTP server).
  • MDA (Mail Delivery Agent): at the receiving end, takes the message from the MTA and places it in the recipient's mailbox.

(b) Role of SMTP

SMTP is the push protocol that moves the mail: from the sender's UA to its mail server and from MTA to MTA. For 100 students the message is submitted once with 100 recipients; the MTA delivers it to each destination mail server (one transfer per receiving server, not necessarily 100). The student then reads the mail from the mailbox using a separate access protocol, POP3 or IMAP (Beyond the deck), not SMTP.

(c) End-to-end vs store-and-forward

  • End-to-end: the sending mail server connects directly over TCP to the receiving mail server and hands the message over, with no third party in between (typical between organisations).
  • Store-and-forward: the message is accepted, stored (queued) on a server, then forwarded to the next server, possibly through intermediate MTAs; if the next server is unreachable it stays queued and delivery is retried. This is why the faculty's mail first sits in a queue.

(d) Transport protocol

TCP (reliable delivery needed for mail). Port 25 for server-to-server transfer, 587 for secure submission (Beyond the deck: 465 for SMTP over TLS). See Unit 2 SMTP.

S5 to S8: TCP congestion, UDP, reliable transfer, Selective Repeat

Background: TCP congestion, UDP, reliable data transfer, ARQ, Unit 3 numericals, Unit 3 question bank.

S5A TCP connection first increases its sending rate rapidly. After some time the network becomes congested and packets are lost. (a) How does TCP detect congestion? (b) How do slow start, congestion avoidance and cwnd affect the sending rate? (c) What happens to cwnd after packet loss? (d) Why is congestion control important for Internet stability?

(a) Detection

TCP infers congestion from packet loss: (1) a retransmission timeout (no ACK arrives in time), the stronger signal; (2) three duplicate ACKs, meaning a later segment arrived but one was missed, the milder signal.

(b) Slow start, congestion avoidance, cwnd

  • cwnd (congestion window) caps how much unacknowledged data the sender may have in flight, so it sets the sending rate (roughly cwnd/RTT). The sender actually limits itself to min(cwnd, rwnd).
  • Slow start: cwnd starts small (1 segment in the course; modern stacks start higher) and doubles every RTT (+1 per ACK) until it reaches ssthresh. Growth is exponential, so the rate rises rapidly.
  • Congestion avoidance: once cwnd reaches ssthresh, it grows by only 1 segment per RTT (additive increase), cautiously probing for spare bandwidth.

Example with ssthresh = 8: cwnd = 1, 2, 4, 8 (slow start), then 9, 10, 11, ... (congestion avoidance).

(c) After loss

Multiplicative decrease: ssthresh is set to half of the current cwnd. On a timeout cwnd falls back to 1 segment and slow start restarts. Beyond the deck On 3 duplicate ACKs (TCP Reno), cwnd is set to the new ssthresh (fast recovery) and the sender continues in congestion avoidance instead of restarting from 1. Example: cwnd = 16 when a timeout occurs gives ssthresh = 8, cwnd = 1; the next growth is 1, 2, 4, 8, then +1 per RTT.

(d) Importance

Without it, every sender would keep pushing data into full router buffers, causing more loss, more retransmissions and even more load (congestion collapse). Backing off on loss and probing gently keeps queues short and shares bandwidth fairly among connections, which keeps the Internet stable.

S6An online multiplayer game uses UDP for player movement. Some packets are lost, but the game does not wait for retransmission. (a) Why is UDP suitable? (b) What is the purpose of the UDP checksum? (c) If the checksum shows a segment is corrupted, what should happen to it?

(a) Why UDP

  • Real-time: a late position update is useless because a newer one replaces it. TCP's retransmission and in-order delivery would stall fresh data behind a lost old packet.
  • Connectionless: no handshake, no connection state; lower delay and overhead (fixed 8-byte header versus 20 or more bytes for TCP).
  • No congestion or flow control throttling the game's steady stream of small updates. The application can tolerate occasional loss, or conceal it itself (e.g. with sequence numbers or prediction).

(b) Checksum purpose

To detect bit errors in the UDP header and data during transmission. The sender takes the segment as 16-bit words, adds them with one's-complement arithmetic and complements the sum; the receiver adds all words including the checksum, and the result must be all 1s (complement all 0s) if no error occurred. Worked example: Unit 3 numericals: checksum. It detects errors only; it cannot correct them.

(c) Corrupted segment

The receiver discards it. UDP does not request retransmission and sends no error back, so the data is simply lost; the game carries on with the next update. Beyond the deck (Some implementations may instead pass a damaged datagram up with a warning, but the standard behaviour is to drop it.)

S7A file-transfer application must send a 10 MB file over a network where packets can be lost, duplicated, corrupted or reordered. Design a basic reliable data transfer mechanism using sequence numbers, acknowledgments, timers and retransmissions, and explain how it detects and recovers from a lost packet.

Mechanism

  • Segmentation and sequence numbers: split the file into numbered packets. With 1000-byte payloads, 10 MB (10,485,760 bytes) is 10,486 packets, the last holding 760 bytes. Sequence numbers let the receiver order packets and discard duplicates.
  • Checksum: the sender adds an error-detection checksum; the receiver drops any corrupted packet (treated as lost).
  • Acknowledgments (ACK): the receiver acknowledges each correct packet (individually or cumulatively).
  • Timer and retransmission: the sender starts a timer for each unacknowledged packet; if it expires before the ACK arrives, the packet is retransmitted.
  • Sliding window (pipelining) Beyond the deck: stop-and-wait would leave the link idle, so the sender keeps up to N packets in flight using Go-Back-N or Selective Repeat (see ARQ notes).

How a lost packet is detected and recovered

  1. Sender transmits packet k and starts its timer.
  2. The packet is lost (or arrives corrupted and is dropped), so the receiver never ACKs it.
  3. The sender's timer expires without an ACK: this is how the loss is detected (a gap in sequence numbers at the receiver, or duplicate ACKs, can reveal it earlier).
  4. The sender retransmits packet k and restarts the timer.
  5. The receiver gets it, ACKs it and delivers data in order. If the original did arrive late, the receiver sees a duplicate sequence number and discards the copy, but still ACKs it.

Sequence-number space Beyond the deck: Go-Back-N needs window size + 1 numbers, Selective Repeat needs at least 2 x window size. This is essentially what TCP does. Compare with Unit 3 Q19.

S8A Selective Repeat sender with window size 4 sends packets 0, 1, 2, 3. Packet 2 is lost but packets 3 and 4 reach the receiver. (a) How does the receiver handle packets 3 and 4? (b) Which packets are retransmitted? (c) Compare with Go-Back-N. (d) Why can Selective Repeat be more efficient when loss is high?

Note: with window 4 the sender first sends 0 to 3. Packet 4 can go out only after the window slides (when packet 0 is ACKed), which is why it arrives after 3.

(a) Receiver behaviour

The receiver window is larger than 1, so out-of-order packets inside the window are buffered. It sends an individual ACK for 3 and for 4, but cannot deliver them to the application yet because packet 2 is missing. Delivery continues in order once 2 arrives (2, 3, 4 together).

(b) Retransmission

Only packet 2, when its own timer expires. Packets 3 and 4 are already acknowledged and are not resent.

(c) Compared with Go-Back-N

  • GBN receiver window is 1: packets 3 and 4 arrive out of order and are discarded (the receiver keeps re-ACKing the last in-order packet, 1).
  • When 2 times out, the GBN sender goes back and resends 2, 3 and 4 (everything from the lost packet onward), even though 3 and 4 had arrived.
  • GBN uses cumulative ACKs and a single timer, and is simple; SR uses individual ACKs, per-packet timers and receiver buffering, so it is more complex. See Unit 3 Q10 and Q11.

(d) Efficiency at high loss

In GBN one loss triggers resending up to a whole window, and the resent packets can themselves be lost, so under heavy loss the link is flooded with redundant copies. SR resends exactly the packets that were lost, so far less bandwidth is wasted. The cost is extra receiver buffer space and per-packet ACK/timer bookkeeping.
