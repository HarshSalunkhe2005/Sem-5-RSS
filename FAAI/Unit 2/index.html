Unit 2 · Topic 1 of 6

Chain-of-Thought (CoT) Reasoning

Step-by-Step Logic

5–6 marks

1Definition / Introduction

Chain-of-Thought is a reasoning strategy where the LLM generates intermediate reasoning steps before arriving at a final answer — making its logic transparent and verifiable. Simple questions ("What is the capital of India?") need no reasoning — direct retrieval. Multi-step problems ("Rahul is older than Aman. Aman is older than Neha. Who is oldest?") demand it — the model must think through relationships first.

2Neat Labeled Diagram — CoT Reasoning Pipeline

Understand the Problem
clarify input, goal, constraints
→
Generate Step 1
outline assumptions
→
Generate Step 2
refine & verify
→
Final Answer
summarize with justification

3Step-by-Step Working — Worked Example

Problem: A shop sells one notebook for ₹50. A student buys 4 notebooks. How much will the student pay?

  1. Cost of one notebook = ₹50
  2. Number of notebooks = 4
  3. Total = 50 × 4 = ₹200

Without CoT the model would just say "₹200" — correct but unverified. With CoT the reasoning is auditable. Logical-reasoning example: "Rahul > Amit, Amit > Neha ⟹ Rahul > Amit > Neha. Final answer: Rahul is the tallest."

4Real-World Example

CoT improves mathematical performance, logical reasoning, and decision-making across coding, planning, and research. Best use cases: mathematics/arithmetic, programming & code debugging, multi-step planning & strategy, data analysis, logic puzzles. Avoid CoT for: simple greetings, basic translations, single-word factual lookups (e.g. "What is 2+2?" needs no CoT).

BenefitWhy it matters
Improved AccuracyReduces logical errors via structured step-by-step thinking
Better ExplainabilityIntermediate steps make reasoning transparent/auditable
Handles ComplexityEnables multi-step problems in math, coding, science
Reliable PlanningSupports structured decisions in medical/financial/engineering contexts

Limitations: slower responses (extra reasoning steps add latency), higher token usage/cost, a wrong assumption still produces a flawed conclusion, and it's overkill for simple tasks.

5Conclusion / Key Advantage

Rule of thumb: use CoT exactly when the task requires multiple logical steps. CoT is the foundation strategy — Self-Consistency and Tree-of-Thought (next topic) are both direct extensions of it, and together they form the backbone of modern AI agent reasoning.

Unit 2 · Topic 2 of 6

Self-Consistency & Tree-of-Thought (ToT) Reasoning

Advanced Prompting Strategies

5–6 marks

1Definition / Introduction

Self-Consistency: generate multiple independent solution paths to the same problem, then select the answer that appears most consistently (majority vote) across them — reducing random errors and increasing confidence. Tree-of-Thought (ToT): explores multiple solution branches, evaluates each, discards (prunes) weaker paths, and advances the most promising one — a search over reasoning paths rather than a single chain.

Self-Consistency: Explore → Compare → Select

Solution 2
(125+75)+50=250 ✓
Solution 3
125+75=190→240 ✗
↓ majority vote
Final Answer: 250

Tree-of-Thought: Branch → Evaluate → Prune → Select

Option A
Celebrity speakers — over budget ✗
Option B
Industry experts — within budget ✓
Option C
Student workshops — lowest cost ✓

Tech-fest example, ₹5-lakh budget → best decision: combine B + C for maximum value within constraints.

3Step-by-Step Working

Self-Consistency pipeline: Receive Problem → Generate Candidates (multiple independent CoT runs) → Evaluate Answers → Find Most Consistent → Return Selected.

ToT pipeline: Understand → Generate (branch into alternatives) → Expand → Evaluate (score each branch) → Prune (discard weak branches) → continue the strongest path.

StrategyPath Structure
Chain-of-ThoughtSingle path, step-by-step
Self-ConsistencyMultiple independent paths, majority vote
Tree-of-ThoughtBranching exploration with evaluation & backtracking

4Real-World Example

Self-Consistency shines in: Mathematics (reliable numerical calculation), Programming (compare generated code solutions), Medical Diagnosis (evaluate diagnostic possibilities), Financial Planning (compare investment strategies), Scientific Research (evaluate competing hypotheses), AI Tutoring (verify explanations before presenting). ToT is used for planning problems with hard constraints, like the Tech Fest budget-allocation example above.

5Conclusion / Key Advantage

CoT develops one solution path; Self-Consistency generates many and votes; ToT searches a branching tree and prunes weak options. All three are the reasoning foundation an autonomous agent needs before it can reliably decide what action to take next — which is exactly the ReAct loop (next topic).

Unit 2 · Topic 3 of 6

The ReAct Framework & Autonomous Agent Loops

Decide → Execute → Observe

6 marks · very high-yield

1Definition / Introduction

A single tool call is not enough for real tasks: the output of Tool A often becomes the input for Tool B, requiring an orchestration layer. The Agent Loop (a practical implementation of the ReAct — Reason + Act — idea) runs continuously: decide → act → observe → re-decide, until the agent determines no further tool calls are needed and a final answer can be generated.

2Neat Labeled Diagram — The Agent Loop Architecture

1 · Decide
evaluate state, pick next action
→
2 · Execute
call the named tool
→
3 · Observe
append result to state
↺

Loop restarts with the updated state until decision["type"] != "tool_call" → break with the final answer.

3Step-by-Step Working

while True:
    decision = get_agent_decision()
    if decision["type"] == "tool_call":
        result = execute_tool(decision["name"], decision["arguments"])
        add_observation(result)
    else:
        break  # Final answer ready

Sequential vs Parallel execution: Tool B waits for Tool A's result when there's a data dependency (e.g. Database query → Search using product name → Calculate comparison). Independent tools (e.g. Weather-Pune + Weather-Mumbai) can run in parallel and be combined afterward — the agent infers this from data dependencies, not from explicit programmer instructions.

Tool Registry pattern (safety): only registered tools can be invoked (explicit allowlist) — the LLM cannot call functions outside the registry boundary, and the executor never uses eval() or runs raw LLM output directly.

Termination controls — every autonomous loop must stop safely:

  • Final Answer Generated — agent determines the task is complete, exits normally.
  • MAX_STEPS Reached — a hard cap (e.g. 5 iterations) prevents infinite loops from runaway reasoning.
  • Tool Failure Limit Exceeded — repeated tool errors trigger a graceful failure report instead of silent looping.
  • High-Risk Action Detected — irreversible/sensitive operations pause and await human approval.

4Real-World Example

User: "Find highest-paid AI employee and convert salary to USD." (1) Database Query → retrieve highest-paid AI employee → ₹12,00,000. (2) Calculator call → convert INR to USD (₹84/$) → $14,285. (3) Generate Answer → synthesize both observations into a final response. Each step depends on the previous observation — a purely sequential chain with no parallelism possible.

5Conclusion / Key Advantage

"An agent loop without termination controls is not a production system — it is a liability." The Decide→Execute→Observe cycle with a bounded, auditable state (user query, tool calls made, observations received, final answer) is what separates a reactive tool-caller from a true autonomous agent, and it is the runtime that Task Decomposition & Planning (next topic) sits on top of.

Unit 2 · Topic 4 of 6

Agent Planning: Task Decomposition & Hierarchical Planning

From Ambiguous Goals to Executable Sub-Tasks

5 marks

1Definition / Introduction

Agent Planning & Task Decomposition is the capability of an autonomous system to dissect an ambiguous, high-level objective into an ordered sequence of executable sub-tasks, establish dependency graphs, and dynamically evaluate and revise plans in response to execution feedback and obstacles. Without decomposition, LLMs suffer from attention dilution — trying to satisfy all sub-requirements simultaneously and failing at fine-grained edge cases.

2Neat Labeled Diagram — Hierarchical Task Network (HTN)

Macro-Goal: Publish Market Intelligence Report
Task 1.0
Research & Discovery
Task 2.0
Quantitative Analysis
Task 3.0
Report Synthesis
tavily_search()
fetch_sec_10k()
python_calc_cagr()
render_pdf_chart()

HTN decomposes a macro-goal → strategic tasks → primitive tool actuators (topological sort across dependencies), preventing context dilution.

3Step-by-Step Working — 4 Planning Methodologies

✂️Task Decomposition

Splits a monolithic prompt into bite-sized sub-goals to avoid attention dilution.

➡️Sequential Planning

Ordered linear pipeline; Step k+1 strictly depends on Step k's state. e.g. ETL pipelines.

🌳Hierarchical Planning (HTN)

Macro-strategy → compound sub-tasks → primitive actions; high-level intent delegated to sub-agents.

🛰️Long-Horizon Planning

Manages tasks spanning hundreds of state transitions; needs persistent checkpoints & context compaction.

Static Plan-and-Solve vs Dynamic Replanning

Plan-and-Solve (static): Planner generates a rigid list upfront → Solver blindly executes with zero mid-stream review. Vulnerability: if a step hits an API rate-limit or missing column, the rigid schedule crashes.

Interleaved ReAct (dynamic): Act → Observe (e.g. 404 error) → Dynamic Replan (Thought: fallback) → google_serp() → Solve. The agent conditions each future action on real empirical results — enabling graceful pivots and retry budgets.

The Reflexion Cycle (Shinn et al.) — Verbal Self-Correction

  1. Detect Failure: Observation returns "Error 404: Endpoint /v1/salaries not found."
  2. Verbal Self-Reflection: "I assumed the REST API followed standard routing. I should check the OpenAPI documentation."
  3. Revised Plan Execution: call_tool("read_api_docs", {"service": "salaries"})

Architecture: Actor (LLM trajectory agent, generates actions τ_t) → Evaluator (checks unit tests / ground truth, computes reward r_t) → Reflexion buffer (verbal critique sr_t cached into rolling in-context memory for Trial t+1). Unlike RL (which needs millions of gradient updates), Reflexion updates behavior in real time via natural-language self-critiques.

4Real-World Example

An AI research agent asked to "Publish a market intelligence report" decomposes the goal into Research → Analysis → Synthesis tasks, each calling its own tools in dependency order. If tavily_search() returns an error mid-way, dynamic replanning (Reflexion) lets the agent verbally diagnose the failure and retry with a fallback tool instead of crashing the whole pipeline — exactly the difference between a rigid script and an autonomous agent.

5Conclusion / Key Advantage

Static planners fail the moment reality diverges from assumptions. Dynamic replanning + Reflexion give an agent environmental resilience — the ability to detect, verbally diagnose, and recover from failure without human intervention, which is essential once the agent starts calling real external tools (next topic).

Tool Integration: APIs, Sandboxed Code & Web Search

Extending Agents Beyond Their Training Data

5–6 marks

1Definition / Introduction

Tool Integration enables an AI agent to interact with external systems — APIs, databases, search engines, code environments — to accomplish tasks beyond its built-in knowledge. Why it's needed: LLMs have a knowledge cutoff (can't access live data), no external access (can't touch software/hardware/private DBs), unreliable math without a calculator tool, and no autonomous action (can't send emails or browse the web on their own).

Decision tree: Needs live data? → Weather API / Search Engine. Needs calculation? → Python Interpreter. Needs stored records? → SQL Database. Needs document reading? → PDF Reader.

3Step-by-Step Working — Types of Tools

🔎Search Engine

Google Search, Tavily — retrieve latest web information.

☁️APIs

Weather, Maps, Flight — access external live services.

🗄️Databases

MySQL, PostgreSQL — retrieve stored records.

🧭Vector DB

FAISS, ChromaDB — semantic document search.

🐍Code Interpreter

Python runtime — execute and evaluate code.

📧Productivity Tools

Gmail API, Google Calendar — send emails, manage events.

query = input("Enter query: ").lower()
if "weather" in query:
    print("Tool: Weather API")
elif "calculate" in query:
    print("Tool: Python Calculator")
elif "pdf" in query:
    print("Tool: PDF Reader")

This "tool router" simulates how an agent maps user intent → tool selection before generating a response — the agent reasons through the query before acting, not after a failed attempt.

4Real-World Example

"Find the cheapest flight from Pune to Delhi tomorrow" → agent calls the Flight API, compares prices, recommends the best option — something an LLM alone cannot do. Real products: ChatGPT (Browsing, Code Interpreter, File Analysis), Microsoft Copilot (Office/Outlook/Teams), Perplexity AI (web search + LLM reasoning), Google Gemini (Workspace integration). Challenges: incorrect tool selection, API failures/rate limits, authentication & security risk, data-privacy and operational cost.

5Conclusion / Key Advantage

Tool Integration is what separates a chatbot from an agent: real-time information access, improved factual accuracy (reduced hallucination), code execution & task automation, and enterprise-system interaction. But calling a tool safely requires the output to be machine-parseable — which is exactly the problem Structured Outputs (next topic) solves.

Structured Outputs: JSON Mode & Function Calling

How LLMs Communicate with Software

6 marks · high-yield

1Definition / Introduction

The problem with normal LLM output: when asked "Find the highest-paid employee," a raw LLM responds with a natural-language explanation plus an embedded SQL query buried in prose — Python can't reliably parse free-form text, there's no deterministic structure to extract, and different runs produce differently-formatted output. Structured Outputs force the model to emit machine-readable JSON that an application can parse deterministically, every single time.

2Neat Labeled Diagram — The Core Pipeline & Gatekeeper Principle

LLM
Generate JSON
→
Runtime
Parse & Validate
→
App
Execute & Return

LLM decides what should happen (never touches the runtime directly) — Application controls what actually happens (validates, gates, executes). This separation is the cornerstone of agent security.

3Step-by-Step Working — Function Calling

  1. Expose Definitions: the application gives the LLM a schema of available functions — names, parameters, descriptions.
  2. LLM Generates Request: the model interprets user intent and emits a structured JSON call targeting one of the defined functions (it cannot invent undeclared parameters).
  3. Validate & Execute: the application validates the request, checks permissions, then executes the real function in its own runtime.
  4. Return Result: the execution result is passed back to the LLM, which composes the final user-facing response.
def get_weather(city: str) -> dict:
    """Get current weather for a city."""
    return weather_api.fetch(city)

# Schema exposed to the LLM:
{
  "name": "get_weather",
  "description": "Get current weather for a city",
  "parameters": {
    "type": "object",
    "properties": { "city": {"type": "string", "description": "City name"} },
    "required": ["city"]
  }
}

Golden rule: the LLM says "Call get_weather with Pune" — it does not execute code. Your app reads the request and decides: if is_allowed("get_weather"): result = get_weather("Pune") else: result = {"error": "Not permitted"}.

4Real-World Example — Why JSON?

PropertyWhy it matters
Machine-ReadableParse with one call — json.loads() in Python, JSON.parse() in JS — no regex
Structured Key-Value PairsEvery field explicitly named — access response["action"] directly
Language-IndependentWorks identically in Python, JS, Go, Ruby, or any HTTP client
API-CompatibleThe universal standard for REST — your agent fits right in

User: "What's the weather in Pune?" → LLM generates {"name":"get_weather","arguments":{"city":"Pune"}} → App executes → returns {"temperature":28,"condition":"Rain"}. The LLM never touches the weather API — it only requests; the application executes.

5Conclusion / Key Advantage

Structured Outputs turn an LLM's fuzzy natural-language intent into a deterministic, Python-ready, API-compatible request — this is the exact mechanism the Agent Loop (Topic 3) uses at the "Decide" step, and the exact mechanism Tool Integration (Topic 5) relies on to safely execute real actions. It is the contract layer that makes the entire agent architecture auditable and secure.
