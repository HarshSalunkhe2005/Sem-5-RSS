Memory Limitations of LLMs & the Context Window

Does an LLM Actually Have Memory?

5 marks

1Definition / Introduction

LLMs don't have unlimited, permanent memory of everything you've told them. They generate responses based only on information available in their current context — relevant conversation must still be present in context to be recalled accurately. This is an architectural constraint, not a cognitive one — not "LLMs forget like humans," but rather "previously-provided information may no longer be available in the model's active context."

2Neat Labeled Diagram — The Context Window

System Instructions
User Messages & Conversation
Retrieved Docs & Tool Results

All three share one fixed-size token budget (the context window) — like a desk with limited space: eventually you can't fit everything.

3Step-by-Step Working

  1. Tokenization: LLMs measure context in tokens (words, subwords, punctuation), not sentences. Context length = maximum tokenized information processed in one interaction.
  2. The long-conversation problem: in very long conversations, older information may be truncated, summarized, or selectively retrieved — "unlimited history" is a myth; there is always a ceiling.
  3. Result: information from earlier messages becomes unavailable or diluted over time.
  4. The agentic-AI problem: if an agent works for hours/days/across multiple conversations, you cannot simply keep putting everything into the context window — agent memory architecture becomes essential (next topic).
StateMemory
Current task info — destination, date, passengers. Tells the agent where it is right now.Persistent info — preferences, past facts. Tells the agent what it remembers across time.

4Real-World Example

Short-Term Memory (key question: "What do I need to know right now?") — user request, current plan, tool results, intermediate results. Long-Term Memory (key question: "What should I retain for future interactions?") — e.g. a flight-booking agent remembering "window seats," "economy class," "morning flights" and recalling them in a later, unrelated conversation session.

5Conclusion / Key Advantage

Understanding the context window as a hard, finite budget — not human-like forgetting — is what motivates every design choice in the rest of Unit 3: structured agent memory tiers (Topic 2) and external retrieval via vector databases / RAG (Topics 3–4) exist specifically to work around this limitation.

Agent Memory Architectures: Short-Term, Long-Term & Reflection

The Cognitive Memory Stack

6 marks · very high-yield

1Definition / Introduction

Agent Memory Architecture is the cognitive storage and retrieval system that organizes an agent's knowledge into Short-Term Working Memory (in-context buffers) and Long-Term Persistent Memory (episodic event streams, semantic knowledge bases, and procedural routines), enabling continuous learning and personalization across sessions.

2Neat Labeled Diagram — Multi-Tier Memory Stack

TIER 1 · WORKING MEMORY — active in-context scratchpad, ~0ms latency

Active user goal · current ReAct step/sub-plan · ephemeral tool observations

↓ consolidate & reflect
TIER 2 · PERSISTENT MEMORY — external datastores, 10–100ms latency

1. Episodic

Autobiographical event logs: "Task #42: Refund rejected (missing doc)." Indexed by timestamp.

2. Semantic

Generalized facts / user profile: "Rahul prefers morning flights, pure veg." Timestamp-independent.

3. Procedural

How-to skills: "To query salary: parse → sanitize → query." Tool schemas & few-shot patterns.

3Step-by-Step Working

Memory Hardware Hierarchy (L1 → L4)

LayerStoreLatencyDurability
L1 · ContextPrompt context (inside GPU forward pass)~0msEphemeral — erased on process end
L2 · KV-CacheIn-memory KV cache (vLLM PagedAttention)~5msSession — recycled across turns
L3 · Vector IndexQdrant/Milvus/Pinecone, HNSW ANN cosine retrieval~25msPersistent — durable for months/years

Memory Decision Protocol (on every new fact)

  1. Is it useful? (Relevance) — filter ephemeral chatter ("ok", "good morning") from durable facts ("I changed my email").
  2. Does it conflict? (Consistency) — check against existing knowledge (e.g. "Vegetarian" vs new "I now eat chicken").
  3. What action? — Insert (new entity), Update/Replace (supersede old fact), or Ignore.

The Generative Agents Retrieval Score (Stanford/Google)

Score = αrecency·Recency + αimportance·Importance + αrelevance·Relevance

  • Recency: exponential decay γΔt — recently accessed memories rank higher.
  • Importance: LLM-assigned poignancy score 1–10 (a marriage proposal = 10, eating breakfast = 1).
  • Relevance: cosine similarity between the query embedding and the stored memory embedding.

4Real-World Example — Reflection Engine

Raw memory stream: 10:05 AM "orders black coffee with oat milk" (importance 2) → 11:30 AM "discusses lactose intolerance" (importance 8) → 2:15 PM "avoids dairy-based dessert" (importance 7). Once accumulated importance crosses a threshold (Σ I(e) > 150), a reflection is triggered: the LLM asks itself "What are the 3 most salient high-level questions about the subjects above?" → generates "Does Rahul have strict dietary/dairy restrictions?" — turning raw episodic events into a reusable semantic insight.

5Conclusion / Key Advantage

Separating memory into Working (fast, ephemeral) vs Persistent (episodic/semantic/procedural, durable) — and scoring retrieval by recency + importance + relevance — lets an agent behave consistently over days or months instead of resetting every conversation. The "Relevance" component (cosine similarity of embeddings) is exactly what Topic 3, Embeddings & Vector Databases, explains in depth.

Embeddings, Vector Databases & Similarity Search

Turning Meaning into Numbers

6 marks · very high-yield

1Definition / Introduction

Computers don't understand words — only numbers. An embedding is a dense numerical vector that captures the semantic meaning of text; similar meanings produce similar (nearby) vectors, letting AI compare ideas, not just keywords. Example: "How do agents remember?" and "Long-term memory stores interactions" use completely different words but mean similar things — keyword search fails here, but embeddings find the match.

3Step-by-Step Working — Code & Distance Metrics

from sentence_transformers import SentenceTransformer
model = SentenceTransformer("all-MiniLM-L6-v2")
sentences = ["Artificial Intelligence is amazing", "AI is fascinating", "I love cricket"]
embeddings = model.encode(sentences)
print(embeddings.shape)  # (3, 384)

from sklearn.metrics.pairwise import cosine_similarity
similarity = cosine_similarity([embeddings[0]], embeddings[1:])
# Higher score = more related — sentence 1 & 2 score highest (same meaning, different words)
import faiss
index = faiss.IndexFlatL2(embeddings.shape[1])
index.add(np.array(embeddings))
query = model.encode(["Artificial Intelligence"])
distances, ids = index.search(np.array(query), k=2)  # nearest-neighbor search

Vector DB vs Traditional DB: SQL = exact match, structured data, WHERE clauses. Vector DB = semantic match, nearest-neighbor search, AI-native (FAISS, Pinecone, ChromaDB, Weaviate, Milvus, Qdrant use HNSW — Hierarchical Navigable Small World — indexing for fast approximate nearest-neighbor lookup across millions of vectors).

4Real-World Example

HR Chatbot case study: Employee asks "How many casual leaves can I take?" → query is embedded → vector DB retrieves the relevant Leave Policy chunk → the retrieved context is injected into the LLM prompt → LLM answers accurately. This exact end-to-end flow (User Question → Embedding → Vector Search → LLM Context) powers everything from "ChatGPT with PDFs" to enterprise chatbots — and is precisely the Retrieval half of RAG (next topic).

5Conclusion / Key Advantage

Embeddings + vector databases let an AI system search by meaning instead of exact keyword match, and scale that search to millions of documents via approximate nearest-neighbor indexes like FAISS/HNSW. This is the retrieval engine that Retrieval-Augmented Generation is built on top of.

Retrieval-Augmented Generation (RAG) & Knowledge Grounding

Grounding LLM Answers in Real Documents

6 marks · very high-yield, likely the anchor question

1Definition / Introduction

LLMs have static knowledge (no access to private documents, real-time data, or domain-specific info) and produce confident hallucinations — plausible-sounding but factually wrong answers with no uncertainty signal. RAG (Retrieval-Augmented Generation) solves this in three steps: Retrieval (find relevant info from external knowledge sources in real time), Augmented (enhance the LLM's prompt with that retrieved context), Generation (produce a grounded, evidence-backed answer using the enriched input).

3Step-by-Step Working — Chunking Strategy

A 500-page PDF cannot (and should not) be sent to the LLM for every query — context windows have limits and flooding them wastes tokens. A chunk is a smaller section of a document, ideally scoped to a single topic, making it independently retrievable — e.g. Chunk 1 = "Introduction," Chunk 2 = "Attendance Policy," Chunk 3 = "Exam Rules"; the query "What attendance is required?" retrieves only Chunk 2.

Chunk SizeTrade-off
Small (~50 tokens)High precision retrieval, but context may be incomplete
Large (~5000 tokens)Better continuity, but irrelevant content + higher token cost

Chunk overlap preserves context across hard boundaries: Chunk 1 = A B C D E, Chunk 2 = D E F G H — tokens D and E bridge the gap so meaning isn't severed mid-sentence. More overlap = better context preservation but higher storage/embedding cost.

RAG vs Fine-Tuning

Fine-tuning bakes knowledge into model weights — slow and costly. RAG retrieves knowledge dynamically at inference time — faster, cheaper, and far more practical when the knowledge base changes frequently (e.g. a policy document updated every semester).

4Real-World Example — Knowledge Grounding

Without grounding: "I think the deadline is the 15th…" — potential hallucination, no source. With grounding: "According to the policy document, the deadline is March 15th." — evidence-based, traceable. Grounding matters most where being wrong is costly: Medical (incorrect clinical info can harm patients), Financial/Legal (regulatory compliance demands accuracy), Education/Corporate (attendance rules, HR policy must be grounded in official documents).

5Conclusion / Key Advantage

RAG transforms an LLM's "I think…" into "According to the evidence…" — combining the reasoning fluency of an LLM with the factual reliability of a live, updatable knowledge base, without the cost of retraining the model. It is the natural endpoint of Unit 3: Memory Limitations (Topic 1) motivate external storage, Agent Memory Architectures (Topic 2) organize it, Embeddings & Vector DBs (Topic 3) make it searchable, and RAG (Topic 4) is the production pattern that ties all three together into a grounded, hallucination-resistant agent.
