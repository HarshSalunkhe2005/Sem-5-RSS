Unit 4 · Topic 1 of 6

Introduction to Multi-Agent Systems

Distributed AI, Collaborative Intelligence & Why Multi-Agent

5 marks

1Definition / Introduction

A Multi-Agent System (MAS) is a system made of several autonomous agents that share an environment, interact with each other, and work (cooperatively or competitively) towards individual and/or common goals. It is a form of distributed AI: intelligence, control and data are spread across many agents instead of being held by one central program. Collaborative intelligence means the group achieves outcomes that no single agent could achieve alone, by combining specialised skills, knowledge and tools. Each agent is typically a Unit 1/2-style agent (LLM + reasoning loop such as ReAct + tools + memory); a MAS adds coordination between them.

3Step-by-Step Working — Why Multi-Agent vs Single Agent

  1. Decompose: a complex goal is broken into sub-tasks (planning, as in Unit 2).
  2. Assign: each sub-task goes to the agent best suited for it (specialised prompt, tools, memory).
  3. Act in parallel / in sequence: agents run their own reasoning loops and call their own tools.
  4. Communicate: agents exchange results, requests and feedback (Topic 2).
  5. Integrate: partial outputs are merged into one final answer; conflicts are resolved by a coordinator or a critic.

Rule of thumb: prefer a single agent for simple tasks; move to multi-agent when the task is complex, needs distinct skills, or benefits from parallel work and review.

4Real-World Example

Trip-planning system: a Flight agent searches flights, a Hotel agent searches stays, a Budget agent checks cost limits, and a Coordinator combines everything into one itinerary. Another example: a software-bug system in which a Developer agent writes a fix and a Tester agent runs the tests and reports back.

5Conclusion / Key Advantage

A MAS replaces one overloaded generalist with a team of cooperating specialists, giving modularity, parallelism, robustness and better quality through review — at the cost of extra coordination. It extends Unit 3's lesson (context windows are finite) by splitting the work and the context across agents, and the remaining topics of this unit explain how they talk (Topic 2), connect to tools (Topic 3), divide roles (Topic 4) and scale (Topics 5–6).

Unit 4 · Topic 2 of 6

Agent Communication

Message Passing, Protocols, Sync vs Async & Blackboard

6 marks · high-yield

1Definition / Introduction

Agent communication is the exchange of information, requests and results between agents so they can coordinate. It rests on message passing: a sender agent builds a structured message and delivers it to one or more receivers, who interpret it and act. A communication protocol fixes the message format, meaning (semantics) and the allowed order of exchanges, so that independently built agents understand one another. Communication is also the way agents share the memory and tool outputs discussed in Unit 3.

3Step-by-Step Working

  1. Compose: the sender creates a message with sender, receiver, intent and content.
  2. Transport: the message is delivered through a channel (in-process queue, message broker, HTTP call).
  3. Interpret: the receiver reads the intent (e.g. request vs inform) and parses the content.
  4. Act: the receiver reasons (ReAct), may call tools, and updates its own memory.
  5. Respond: the receiver replies (answer, agree, refuse, failure) and the conversation continues or ends.

Communication protocols

  • FIPA-ACL (Agent Communication Language): classic standard from the Foundation for Intelligent Physical Agents, based on speech acts. Each message carries a performative stating the intent. Common performatives: inform (tell a fact), request (ask for an action), query-if / query-ref (ask for information), propose, accept-proposal, reject-proposal, cfp (call for proposal), agree, refuse, failure.
  • JSON messages (modern LLM agents): agents exchange structured JSON (or natural language wrapped in JSON) with fields such as role, type and content; easy to validate and log.
  • A2A-style protocols (Agent2Agent): an open protocol for agents built by different vendors to discover each other (via a public "agent card" describing capabilities), send tasks and receive results over standard web transport (HTTP, JSON-based messages). It focuses on agent-to-agent talk, whereas MCP (Topic 3) focuses on agent-to-tool access.
// FIPA-ACL style (simplified)
(request :sender planner :receiver researcher
         :content "find top 3 papers on RAG" :language text)

// JSON message style
{ "from": "planner", "to": "researcher",
  "type": "request", "content": "find top 3 papers on RAG" }

4Real-World Example

Customer support: a Triage agent sends a request to a Billing agent ("check refund status of order #123"); the Billing agent calls its tools and replies with an inform containing the result, or a refuse / failure if it cannot. In a blackboard variant, a research team writes findings, partial drafts and open questions to a shared board, and each specialist picks up whatever it can improve — a classic pattern for complex problems with no fixed order of steps.

5Conclusion / Key Advantage

Well-defined messages and protocols make agents interoperable and their behaviour auditable. Choose message passing for directed, scalable, auditable exchanges and a blackboard for opportunistic, shared-workspace collaboration; choose asynchronous communication for scale and long tasks, synchronous for simple dependent steps. The next topic, MCP, standardises the other kind of communication — agent to tools and data.

Unit 4 · Topic 3 of 6

Model Context Protocol (MCP)

A Standard Way to Connect Agents to Tools & Data

6 marks · very high-yield

1Definition / Introduction

The Model Context Protocol (MCP) is an open standard (introduced by Anthropic) that defines one common way for AI applications to connect to external tools, data sources and prompts. It is often described as a "USB-C port for AI": build a tool connector once as an MCP server and any MCP-capable application can use it.

Motivation — the N × M integration problem: without a standard, every AI application (N) needs custom glue code for every tool or data source (M), i.e. N × M separate integrations to build and maintain. With MCP each application implements the client side once and each tool implements the server side once, so the work becomes N + M. This builds on Unit 2's tool calling: MCP standardises how tools are described, discovered and invoked.

3Step-by-Step Working

Architecture components

  • Host: the user-facing AI application (chat assistant, IDE, agent app) that contains the LLM, manages clients and enforces user consent/security.
  • Client: a connector inside the host that keeps a 1-to-1 connection with one MCP server.
  • Server: a lightweight program that exposes capabilities of a system (file system, database, GitHub, web API, etc.) through the protocol.
  • Tools: executable functions the model can decide to call (e.g. search_flights); may have side effects.
  • Resources: read-only data the application can load as context (files, records, documents) — connects to Unit 3 grounding / RAG context.
  • Prompts: reusable, parameterised prompt templates the user can invoke (e.g. a "summarise this PR" template).

Lifecycle

  1. Connect & initialise: client and server open a connection, exchange protocol version and declare capabilities (initialize).
  2. Discover: client lists what the server offers (tools/list, resources/list, prompts/list); tool descriptions and JSON schemas are given to the LLM.
  3. Decide: the LLM, in its ReAct loop, chooses a tool and arguments for the user's request.
  4. Invoke: the host (after any needed user approval) sends tools/call through the client; the server runs the action.
  5. Return: the result is sent back and added to the LLM context; the loop continues until the task is done.
// Request (client -> server)
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "city": "Pune" } } }

// Response (server -> client)
{ "jsonrpc": "2.0", "id": 1,
  "result": { "content": [ { "type": "text", "text": "31 C, clear" } ] } }

Transport — JSON-RPC

All MCP messages use JSON-RPC 2.0 (requests with id, responses, and one-way notifications). Two standard transports:

  • stdio: the host launches the server as a local subprocess and exchanges messages over standard input/output — simple, fast, best for local tools.
  • HTTP (Streamable HTTP, earlier HTTP + SSE): the server runs remotely and clients talk to it over HTTP, with streaming for server-to-client messages — suited to remote, shared, multi-user servers (with authentication).

4Real-World Example

Coding assistant: an IDE (host) connects through clients to a GitHub MCP server, a database MCP server and a file-system MCP server. Asked "find failing tests and open an issue", the LLM lists the available tools, reads files via resources, calls the test/database tools, then calls the GitHub create_issue tool — with no custom integration code written for that IDE. The same servers can be reused unchanged in a chat application or in a multi-agent system, where each agent gets the set of MCP tools relevant to its role.

5Conclusion / Key Advantage

MCP removes the N × M integration burden and gives agents a standard, discoverable, interoperable way to use tools and data: write a connector once, use it with any compliant host or agent, swap models or applications freely, and keep a central place for permissions and security (user consent, least privilege). Together with agent-to-agent protocols (Topic 2), it forms the interoperability layer of modern agentic systems.

Unit 4 · Topic 4 of 6

Agent Roles & Collaboration Models

Planner, Executor, Research & Critic Agents

6 marks · high-yield

1Definition / Introduction

In a multi-agent system each agent is given a role — a defined responsibility expressed through its system prompt, tools, memory and permissions. A collaboration model defines how these role-agents are organised and how they work together: hierarchical (a manager delegates to workers), role-based (a team of specialists with fixed duties) and cooperative problem solving (agents share a common goal and jointly build the solution). Splitting roles reduces each agent's context load and lets each be tuned for one job.

3Step-by-Step Working

RoleResponsibilityTypical tools / memory
PlannerUnderstands the goal, breaks it into ordered sub-tasks, assigns them, replans when something failsPlanning prompts; task list / plan state
ExecutorCarries out a sub-task: calls tools/APIs, writes code, performs the action, reports the resultTool calling, MCP servers, code runner
ResearchFinds and summarises the information needed: web search, document retrievalSearch tools, vector DB / RAG (Unit 3)
CriticChecks outputs for correctness, completeness and policy; gives actionable feedback or approvesRubrics, test runners, fact-checking against sources
  1. Plan: the Planner turns the user goal into sub-tasks.
  2. Research: the Research agent retrieves the facts and context required.
  3. Execute: the Executor performs the actions using tools.
  4. Critique: the Critic evaluates the result against the goal and criteria.
  5. Iterate or finish: on failure the feedback goes back and the cycle repeats (with an iteration limit); on success the result is returned.

Collaboration models

  • Hierarchical structure: a tree of authority — a manager/supervisor agent decomposes work and delegates to sub-agents (which may have their own sub-agents) and aggregates their results. Clear control and accountability; the manager can become a bottleneck or single point of failure.
  • Role-based collaboration: agents are defined by fixed roles (like a software team: product owner, developer, tester); communication follows the role structure and workflow (sequential pipeline, or round-table discussion).
  • Cooperative problem solving: agents share one goal, exchange partial results and knowledge, and may negotiate or vote (via messages or a blackboard from Topic 2); the solution emerges from combining contributions. Contrast with competitive setups (debate, adversarial) where agents argue to improve quality.

4Real-World Example

Writing a market report: the Planner outlines sections; the Research agent retrieves facts via RAG; the Executor drafts text and builds tables/charts using tools; the Critic checks claims against the retrieved sources and flags unsupported statements; the draft is revised until the Critic approves. In code generation, the Critic is often a Tester agent that executes unit tests and returns failures to the Executor.

5Conclusion / Key Advantage

Clear roles plus a defined collaboration structure give focused prompts, easier debugging, and built-in quality control through the Critic loop. Hierarchy provides control; role-based teams provide specialisation; cooperative problem solving provides combined intelligence. When no central manager exists and coordination is purely local, we move to swarm approaches (next topic).

Swarm Intelligence & Real-World Applications

Decentralized Coordination & Emergent Behaviour

6 marks

1Definition / Introduction

Swarm intelligence is the collective behaviour of many simple agents that follow local rules and interact only with neighbours and their environment — with no central controller (decentralized coordination). Complex, useful group-level patterns arise that no individual agent plans or understands: emergent behaviour. Inspiration comes from nature: ant colonies, bird flocks, fish schools, bee swarms.

3Step-by-Step Working

ExampleLocal rule(s)Emergent result
Ant colonyWander; on finding food return to the nest laying pheromone; follow stronger pheromone; pheromone evaporatesShortest path to food emerges (basis of Ant Colony Optimization)
Boids (flocking)Separation (avoid crowding), Alignment (match neighbours' heading), Cohesion (move toward neighbours' centre)Realistic, coordinated flock movement with no leader
StigmergyAgents modify the environment; the modified environment guides the next actionIndirect coordination without direct messaging (e.g. pheromone trails, termite nests, shared documents/state)
  1. Many agents are initialised with identical simple rules and limited local perception.
  2. Each agent senses neighbours / environment and acts; no agent has the global picture.
  3. Actions change the environment (markers, positions, shared state), which influences other agents (positive feedback reinforces good paths; evaporation/decay removes bad ones).
  4. Global order emerges over iterations: a solution, pattern, or consensus.

Properties: robustness (loss of some agents is tolerated), scalability (add more agents), flexibility (adapts to change), low individual complexity. Limits: hard to predict or debug emergent behaviour, slower convergence, harder to guarantee exact outcomes than with a central planner (Topic 4).

Real-world applications of multi-agent / agentic systems

🔎 Autonomous Research Assistants

Multiple agents search, read and summarise sources in parallel (RAG + web tools), a synthesiser merges findings and a critic checks citations against the retrieved sources.

💻 Software-Development Agents

Planner breaks down the feature, coder agents implement, tester agent runs tests, reviewer agent critiques; tools (repo, shell, CI) are accessed through tool calling / MCP.

🏢 Business-Automation Agents

Agents handle workflows such as support triage, invoice processing, scheduling and report generation by coordinating CRM, email and database tools, with human approval for sensitive steps.

4Real-World Example

Warehouse / drone swarms and routing: many simple robots or vehicles coordinate through local rules and shared signals to cover an area or find efficient routes without a central dispatcher; Ant Colony Optimization is used for routing problems. For LLM agents, the analogy is many lightweight worker agents that read and update a shared state or task board (stigmergy-like), picking up open work without a manager assigning each task.

5Conclusion / Key Advantage

Swarm intelligence shows that sophisticated behaviour can emerge from simple agents and local interaction, giving decentralized, robust and scalable coordination. In practice, agentic applications (research, software development, business automation) often blend structured roles (Topic 4) with swarm-like parallelism and shared state, choosing control vs flexibility according to the task.

Deployment Considerations

API-Based Deployment, Monitoring & Logging, Scaling

5 marks

1Definition / Introduction

Deployment is moving an agent or multi-agent system from a prototype to a reliable service that real users and other systems can call. Key concerns are how it is exposed (API-based deployment), how it is observed (monitoring and logging) and how it handles growth (scaling). Agents are harder to operate than ordinary software because they are non-deterministic, multi-step, call external tools, and cost money per LLM call.

3Step-by-Step Working

1. API-based deployment

  • Wrap the agent behind a standard interface (typically REST/HTTP API, e.g. built with FastAPI/Flask) so any client can send a request and receive a response; use streaming for long responses and async jobs (submit task → poll or webhook) for long-running agent tasks.
  • Package with containers (Docker) and run on cloud / Kubernetes / serverless; keep configuration and API keys in environment variables or a secrets manager, never in code.
  • Add authentication, authorization and rate limiting; apply least-privilege to tools (MCP servers) and require human approval for risky actions; validate inputs and outputs (guardrails, prompt-injection defence).
  • Version prompts, models and tools so changes can be rolled back.

2. Monitoring & logging

  • Logging: record each request, prompt, model response, tool call (name, arguments, result), error and final output, with a trace/correlation ID tying a multi-agent run together — essential for debugging non-deterministic behaviour and for audit. Mask sensitive data/PII.
  • Metrics: latency, error rate, token usage and cost per request, tool-call failure rate, number of loop iterations, task success rate.
  • Tracing: view the full chain of reasoning steps and agent-to-agent messages.
  • Evaluation & alerts: monitor output quality (hallucination, user feedback, automated evals) and alert on spikes in errors, cost or latency; set limits on iterations and spend to stop runaway agent loops.

3. Scaling agent systems

  • Horizontal scaling: run many identical, stateless agent instances behind a load balancer; keep conversation state and memory externally (database, vector store, cache — Unit 3) so any instance can serve any request.
  • Queues & async workers: use a message queue to absorb bursts and run long tasks in the background; supports asynchronous agent communication (Topic 2).
  • Cost and latency control: cache repeated results, use smaller/cheaper models for simple steps, limit context size, batch and parallelise independent sub-tasks, respect LLM API rate limits with retries and back-off.
  • Reliability: timeouts, retries, fallbacks (alternate model or tool), graceful degradation, and per-agent isolation so one failing agent does not bring the whole system down.

4Real-World Example

Customer-support agent service: exposed as a REST endpoint behind an API gateway, running as several container replicas; chat history is stored in an external database and knowledge in a vector DB; tool access goes through MCP servers with limited permissions. Every run is logged with a trace ID, dashboards show latency and token cost, an alert fires if error rate rises, and replicas are added automatically at peak hours while a queue handles heavy back-office tasks.

5Conclusion / Key Advantage

A production agent system needs more than a good prompt: a clean API, strong observability (logs, metrics, traces) and a scalable, secure architecture with controlled cost. These practices make multi-agent systems dependable, debuggable and affordable, completing the journey of Unit 4 from agent teams and protocols (MCP, A2A-style messaging) to running them in the real world.
